# 비교 분석: revfactory/harness vs 이 프로젝트

조사일 2026-10-01 · 대상 [revfactory/harness](https://github.com/revfactory/harness) v2.1.0 (Apache 2.0)

## 0. 왜 비교했는가

이 프로젝트의 가장 약한 지점은 **검증 기준의 근거**였다. 가중치 40/30/20/10 과 합격선 75점은
경험적 도출 없이 선언된 상수이고, "통과"라는 판정이 임의적이라는 지적을 받았다.
같은 이름을 쓰는 외부 프로젝트가 이 문제를 어떻게 다루는지 확인해 **차용할 근거**를 찾는 것이
비교의 목적이다.

## 1. 확인한 사실 (추측 아님)

GitHub API 로 파일 트리를 받아 전수 확인했다.

| | revfactory/harness | 이 프로젝트 |
|---|---|---|
| 파일 수 | 29개 | — |
| **실행 코드** | **0줄** (Python/JS 없음) | 하네스 코어 **4,038줄** + 검증 스크립트 850줄 |
| 주 산출물 | `skills/harness/SKILL.md` 35.7KB + 레퍼런스 8종 약 130KB | LangGraph 런타임, 도구 15종, 증거 게이트 |
| 배포 형태 | Claude Code 플러그인 (`.claude-plugin/`, marketplace.json) | 로컬 CLI (`main.py`, `night_shift.py`) |
| 프로젝트 위생 | LICENSE(Apache 2.0), CHANGELOG 14.4KB, CONTRIBUTING, 이슈/PR 템플릿 | **LICENSE·CHANGELOG·CONTRIBUTING 없음**, 버전 표기 없음 |
| 실패 기록 | CHANGELOG (변경 이력) | `troubleshooting/` 9건 648줄 (증상→원인→수정→검증→예방) |
| 미디어 | GIF/MP4 약 21MB | 없음 |

**같은 이름을 쓰지만 다른 종이다.** revfactory 는 "Claude Code 팀 아키텍처 공장" —
도메인 설명을 받아 에이전트 팀과 스킬 **설정을 생성해주는 지식 산출물**이다.
이 프로젝트는 기능 명세를 받아 **코드를 구현하고 검증하는 실행 시스템**이다.
어느 쪽이 우월한 문제가 아니라, 서로 없는 것이 다르다.

## 2. 그들이 가진 것 중 우리에게 없던 것

### 2.1 개입의 효과를 수치로 주장한다 (핵심)

README 는 v1 성과를 이렇게 적는다 — 15개 소프트웨어 엔지니어링 과제에서
**평균 품질 49.5 → 79.3 (+60%), 승률 15/15, 산출 분산 −32%**.
그리고 곧바로 "저자가 측정한 수치이며 독립적인 파일럿 검증이 필요하다"고 단서를 붙인다.

우리 프로젝트는 **하네스가 효과가 있는지 한 번도 측정하지 않았다.**
TS-001~008 은 전부 "장치가 고장났고 고쳤다"는 기록이지,
"장치가 있는 편이 없는 편보다 낫다"는 증거가 아니다.

### 2.2 검증 방법론이 문서화되어 있다

`skills/harness/references/skill-testing-guide.md` (15.9KB) 의 요지:

- **블라인드 A/B**: with-skill / without-skill 을 동시 실행하고, 슬롯 순서를 무작위화하며
  채점자에게 어느 쪽이 처리군인지 숨긴다.
- **단정 기반 채점**: `{text, passed, evidence}` 스키마로 조건별 통과 여부와 **근거**를 남긴다.
- **판별력 원칙**: *"스킬을 쓰지 않아도 언제나 통과하는 조건은 좋지 않다."*
- **경계 사례 의무**: 트리거 검증에 should-trigger 10건 + should-NOT-trigger 10건,
  특히 **near-miss**(표현은 비슷하나 적용 대상이 아닌 경우)를 중시한다.
- **측정 즉시 기록**: `total_tokens`, `duration_ms` 는 완료 통지 직후 저장한다 — 나중엔 복구 불가.
- **과적합 방어**: 프롬프트 자동 최적화 시 60% 학습 / 40% 평가 분리, 최대 5회 반복.

이 중 **판별력 원칙**과 **단정 기반 채점**은 우리가 TS-008 에서 독립적으로 도달한 결론과
같다(기능 ID 태그 + `evidence_tests` 기록). 서로 다른 출발점에서 같은 지점에 도달했다는 것은
그 방향이 옳다는 **수렴 증거**다. 반면 **판별력을 수치로 입증하라**는 요구는 우리에게 없었다.

### 2.3 적응 기제가 명시적이다

`/harness:evolve` 는 초기 설정과 현재 설정의 델타를 포착해 피드백을 에이전트·스킬·오케스트레이터로
**일반화**한다. 우리 쪽 대응물은 Reflexion(기능 단위, 일회성)과 `troubleshooting/`(사람이 수동 작성)뿐이다.

## 3. 세운 기준 (측정 가능한 형태로)

비교에서 끌어낸 네 가지를 이 프로젝트의 기준으로 채택한다.

### 기준 1 — 판정 기준은 판별력을 수치로 입증해야 한다
> 모든 입력을 통과시키는 기준은 기준이 아니다.

**측정 방법**: `python -m harness.metrics` — 증거 수준별로 전체 기능을 판정해 통과율을 센다.
**합격 조건**: baseline(`suite`) 통과율이 100% 에 가깝고 treatment(`feature`) 통과율이
현저히 낮아야 한다. 둘이 같다면 새 기준은 아무것도 하지 않는 것이다.

### 기준 2 — 통과에는 근거가 함께 기록되어야 한다
`features.json` 의 각 통과 항목은 `evidence_tests`(근거 테스트 이름)와
`steps_covered` / `steps_uncovered` 를 갖는다. 사람이 그 이름으로 다시 돌려 반증할 수 있어야 한다.

### 기준 3 — 경계 사례(near-miss) 음성 대조가 의무다
태그 매칭은 `F-004` 가 `F-0041` / `F-004b` / `XF-004` 에 걸리지 않아야 한다.
`repro_ts008.py` 가 이 음성 대조를 12건 포함한다. 통과만 확인하는 테스트는 기준을 보증하지 못한다.

### 기준 4 — 측정값은 발생 즉시 기록한다
종료 상태와 소요 시간은 `night_shift` 가 `finally` 에서 **항상** `[END]` 줄로 남긴다.
토큰 사용량은 현재 기록하지 않는다 — **미해결 격차로 명시한다**(§6).

### 그리고 정직성 규약
자기 측정 수치에는 "저자 측정, 독립 검증 필요" 꼬리표를 붙인다. 아래 §4 의 수치도 그렇다.

## 4. 측정 결과 (저자 측정, 독립 검증 필요)

`python -m harness.metrics --project ./web_target` 실행 결과. LLM 호출 없음, 언제든 재현 가능.

### 4.1 증거 게이트의 판별력 — A/B

| 수준 | 통과 | 거부 | 통과율 | 주요 거부 사유 |
|---|---|---|---|---|
| `suite` (TS-006 동작) | **75** | 0 | **100.0%** | — |
| `feature` (TS-008, 기본) | **5** | 70 | **6.7%** | 기능 태그 없음 70 |
| `step` (최고 엄격도) | **1** | 74 | **1.3%** | 기능 태그 없음 70, 단계 미검증 4 |

**판별력 93.3%** — baseline 이 통과시킨 75건 중 70건은 근거 없는 통과였다.
즉 TS-006 시점의 게이트는 *"스위트가 녹색이면 75개 기능 중 무엇이든 완료로 기록할 수 있는"* 상태였다.
기준 1을 통과한다: baseline 100% → treatment 6.7%.

### 4.2 실행 로그 사후 측정

| 항목 | 값 |
|---|---|
| 총 시도 | 15회 |
| 종료 상태 기록됨 | 6회 (40%) |
| **종료 상태 미기록** | **9회 (60%)** |
| 소요 시간 중앙값 | 312초 |
| 최단 시도 | 7초 (= 쿼터 초과로 즉시 실패, TS-005) |

60% 가 측정 맹점이었다. `[END]` 기록을 `finally` 에 넣어 수정했고(TS-009),
성공·인프라 장애·타임아웃·예외 네 경로 모두 기록되는 것을 확인했다.

## 5. 채택하지 않은 것과 이유

| 항목 | 판단 |
|---|---|
| 블라인드 LLM 채점 패널 | `features.json` 의 통과 판정에 LLM 이 **전혀 개입하지 않으므로**(jest 결과만 사용) 블라인딩할 대상이 없다. 단, Evaluator(P-04)의 점수에는 적용 가치가 있다 — §6 |
| `/harness:evolve` 자동 일반화 | 측정 루프가 먼저 서야 한다. 효과를 못 재는 상태에서 프롬프트를 자동 수정하면 회귀를 감지할 수 없다 |
| Progressive Disclosure | 그들은 130KB 가이드를 다루므로 필요하다. 우리 코더 시스템 프롬프트는 **3,151자(약 1,260토큰)** 로 이미 간결하다 — 측정해보니 우리 문제가 아니었다 |
| 플러그인/마켓플레이스 패키징 | 배포 모델이 다르다 (실행 런타임 vs 설정 생성기) |
| 60/40 학습·평가 분리 | 프롬프트 자동 최적화를 하지 않으므로 현재 적용 대상이 없다. 도입 시 필수 |

## 6. 남은 격차 (정직하게)

비교로 **드러났지만 아직 닫지 못한** 것들.

1. **토큰·비용 측정이 없다.** 그들은 완료 직후 `total_tokens` / `duration_ms` 를 저장하라고
   명시한다. 우리는 기능당 비용을 모른다 — 모델 비교(pro vs flash)를 하려면 반드시 필요하다.
2. **하네스 유무의 A/B 를 실제로 돌리지 못했다.** §4 는 *게이트 기준*의 A/B 이고,
   *하네스 전체*의 효과(하네스로 구현 vs 맨 LLM으로 구현)는 측정하지 않았다.
   Gemini 프로젝트가 월 지출 한도에 걸려 있어 실행 자체가 불가능하다(TS-005).
   측정 설계는 서 있으나 수치는 없다.
3. **Evaluator 의 LLM 채점은 여전히 근거 없는 상수에 의존한다**(가중치 40/30/20/10, 75점).
   블라인드 채점·채점자 간 일치도 측정을 적용할 지점은 여기다. 다만 이제
   `features.json` 의 플래그가 이 점수에 의존하지 않는다 — 분리되어 있다.
4. **프로젝트 위생**: LICENSE, CHANGELOG, 버전 표기가 없다. 공개·인용 가능한 산출물로
   쓰려면 필요하다. 라이선스 선택은 소유자의 결정이라 임의로 추가하지 않았다.
5. **태그된 테스트가 제대로 검증하는지는 여전히 보지 않는다.**
   `expect(true).toBe(true)` 에 `F-004.5` 를 붙이면 통과한다 (TS-008 의 남은 주관성).

## 7. 결론

차용할 가치가 가장 큰 것은 특정 기능이 아니라 **"개입의 효과를 수치로 주장한다"는 태도**였다.
그 태도를 우리 게이트에 적용해 처음으로 숫자가 나왔다 — 판별력 93.3%.
이 숫자는 "우리 게이트가 옳다"는 증명이 아니라,
**"게이트를 끈 상태와 비교해 실제로 다른 일을 한다"는 반증 가능한 측정**이다.
그 차이가 이 비교의 수확이다.
