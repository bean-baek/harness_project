## Symptoms
사용자가 물었다 — *"하네스 엔지니어링 자체에서 실수가 많지 않냐"*. 23건을 가족으로
묶어 세어 보니 **16/23 (70%) 이 세 가족의 반복**이었고, 그중 가장 나쁜 사례가 나왔다.

README 가 **같은 기능의 같은 측정값을 네 번 다르게** 발표했다. 이틀 사이다.

```
a53966f  2026-10-02  F-005 돌연변이 점수 50%  (잡음 2 / 생존 2 / 폐기 2)
fed5ac1  2026-10-02                    40%  (잡음 2 / 생존 3 / 폐기 0)
6d66152  2026-10-03                    33%  (잡음 5 / 생존 10 / 타입 1)
5189a3d  2026-10-03                    50%  (잡음 3 / 생존 3 / 명세밖 3)
```

매번 측정 코드를 고쳤고(TS-021·022·023), 매번 산문의 수치를 **손으로** 갱신했고,
한 번은 갱신을 빠뜨려 **33% 와 50% 가 같은 문서에 동시에** 들어 있었다
(README 245줄·271줄). 서사 순서로는 설명되지만 읽는 사람에게는 모순이다.

같은 조사에서 더 많이 나왔다 — §2 모드 표의 "회귀 326건" 은 **이미 낡은 값**이었다
(당시 실제로는 661). 판별력 92%, 기능 6/75, jest 51/51, 교차검증 5·단일채널 1,
회귀 661건, 실패 모드 23건 — 전부 산문에 박힌 시점 수치였다.

## Root cause
**죽은 설정과 같은 구조다** (TS-007 / TS-019): 문서가 값을 주장하고 **코드가 그것을
모른다.** 측정 코드를 고치면 산문은 즉시 거짓이 되는데 아무도 알려주지 않는다.

그 패턴은 이미 `deadcode.py` 로 기계화해 막았다. 같은 처방을 쓰지 않은 이유는
"문서의 수치"를 설정이 아니라 **글**로 취급했기 때문이다. 둘의 구조는 같다.

하네스의 일은 **믿을 수 있는 수치를 만드는 것**이다. 이틀간 틀린 수치를 자신 있게
내놨다. 측정 코드의 버그(TS-021~023)보다 이것이 더 나쁘다 — 버그는 고치면 끝이지만
발표된 거짓 수치는 **읽은 사람에게 남는다.**

## Fix — 생성 파일 + 드리프트 차단
### `harness/status.py` + `cli status [--check]`
살아 있는 측정값은 **`docs/status.md`** 에만 둔다. `cli status` 가 생성하고,
`cli status --check` 가 재생성해 커밋된 내용과 다르면 **종료 코드 1** 을 돌린다.
CI 가 그것을 돌린다.

락파일 검사와 같은 방식이고 **오탐이 구조적으로 불가능하다** — 같은 입력에서 같은
문자열이 나오는지만 본다. 지금까지 만든 검사기들(TS-017·019·020·022)은 전부 휴리스틱의
오탐을 걱정해야 했는데, 이건 그 걱정이 없다.

실측 비용: 판별력 9.3초 + 검수 10.4초 + 자기 감사 4.0초 + 독립성 2.5초 ≈ **26초**.
CI 에 한 번 추가하기에는 허용 범위다.

### 비싼 측정은 **값을 발표하지 않는다**
| 측정 | 대신 싣는 것 | 이유 |
|---|---|---|
| 돌연변이 점수 | `cli mutate <기능>` | 기능당 약 47초. 매 CI 에 못 돌리고, 돌리지 않으면 **검증되지 않은 수치**가 된다 |
| 회귀 검증 건수 | 각 스크립트 실행 | 전부 돌리면 분 단위. CI 가 종료 코드를 이미 확인하므로 '총 n건'은 검증 없이 떠다니는 값이었다 |
| 커버리지 % | `npm test` | 임계 미달로 종료 코드가 1 이어서 통과/실패와 수치가 섞인다 (TS-012) |

**검증되지 않는 수치를 발표하지 않는 것**이 이 파일의 목적이다. 이것이 핵심 결정이다 —
드리프트를 막는 더 쉬운 길은 "더 자주 갱신하기"지만 그건 사람의 기억에 의존한다.

### 산문에서 걷어낸 것
README 양쪽에서 시점 수치를 전부 제거하고 `docs/status.md` 를 가리키게 했다.
`verification/README.md` 의 건수 열도 제거했다.

**역사적 수치는 남긴다** — 고친 결함의 '전' 값은 드리프트하지 않는다.
`190곳 중 3곳`(TS-021 의 연산자), `콜드 10.8초 / 웜 1.9초`, `359줄 중 4줄`(TS-018),
`보호 경로 4개 중 3개 생존`(TS-022 실험)은 그 시점의 기록이고 영구히 참이다.
`tools.py 15%` 처럼 애매한 것은 **"TS-018 시점 측정"** 이라고 명시했다.

## Prevention
- **문서가 주장하는 값은 코드가 알아야 한다.** 설정이든 측정값이든 같다.
  문서와 코드가 어긋날 수 있는 모든 자리에 기계적 비교를 둔다 (TS-007·019·024).
- **검증할 수 없는 수치는 발표하지 않는다.** 매 CI 에 재측정할 수 없다면 값 대신
  **산출 명령**을 싣는다. "더 자주 갱신하자"는 사람의 기억에 의존하는 처방이다.
- **드리프트 검사는 생성-후-비교로 만들 것.** 휴리스틱 검사기는 오탐을 걱정해야 하지만
  (TS-017·019·020·022 에서 전부 겪었다) 같은 입력→같은 문자열 비교는 그 걱정이 없다.
- **걷어낸 뒤 다시 들어오는 것을 막을 것.** 수치를 제거하는 작업만으로는 재발한다.
  패턴 스캔을 회귀에 넣어야 다음에 넣는 순간 CI 가 막는다.
- **역사적 수치와 시점 수치를 구분할 것.** 고친 결함의 '전' 값은 영구히 참이고 남겨야
  한다. 애매하면 **"언제 측정한 값"** 이라고 명시한다.
- **세 번 반복된 가족은 가드를 만들라는 신호다.** "선언했는데 돌지 않는다"는 네 번째
  발생에서야 CI 가 생겼고(TS-012), 죽은 설정은 두 번째에서 `deadcode.py` 가 생겼고
  (TS-019), 측정의 거짓말은 **다섯 번째**에서야 이 가드가 생겼다
  (TS-009·015·021·022·023 → 024). 매번 늦었다.
