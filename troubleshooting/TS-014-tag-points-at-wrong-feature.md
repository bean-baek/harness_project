## Symptoms
E2E 를 처음 실행하며(TS-012) 발견한 네 건의 실패를 분류하다 두 문제가 드러났다.

**(1) 태그 오기** — `web_target/tests/smoke.spec.ts` 의 라벨 3건이 명세와 전혀 달랐다.

| 스펙 라벨 | features.json 의 실제 명세 |
|---|---|
| `F-017: 성능 기준` | 경쟁 종료 시 승자에게 디지털 배지와 보상을 부여한다 |
| `F-018: 키보드 접근성` | 대시보드에 주간 완료 통계 차트가 표시된다 |
| `F-020: 네트워크 오류` | 읽지 않은 알림 수를 벨 아이콘에 뱃지로 표시한다 |

게이트는 ID 문자열만 맞으면 통과시키므로 **이 오기를 전혀 보지 못한다.**
E2E 가 증거로 계수되는 순간 엉뚱한 기능에 크레딧이 간다.

**(2) 범위 문제** — 나머지 실패는 피험체(web_target)의 결함이었다.
"하네스 검증 프로젝트에서 임의로 생성된 앱의 결함을 어디까지 고치는가"라는 판단이 필요했다.

## Root cause
- **태그 검증 부재**: TS-008 이 "기능 ID 를 인용하는 통과 테스트"를 증거로 정의했지만,
  **ID 와 명세의 대응은 아무도 확인하지 않았다.** ID 는 기계가 맞추고 라벨은 사람이 쓴다 —
  그 사이가 비어 있었다.
- **판단 기준 부재**: `web_target` 은 결과물이 아니라 피험체인데, 결함이 나올 때마다
  고치면 하네스 작업이 앱 작업으로 전이된다. 반대로 전부 무시하면 측정 도구가 녹슨다.

## Fix
### 하네스 — 태그 린터 (`harness/tags.py`, `cli tags`)
`describe` 라벨을 명세 설명과 문자 2-gram 으로 대조해 세 가지를 **보고**한다.

| 검사 | 성격 |
|---|---|
| `unknown-id` | features.json 에 없는 ID 인용 — 정확 (종료 코드 1) |
| `label-mismatch` | 라벨이 명세와 거의 겹치지 않음 — 휴리스틱 (보고만) |
| `label-unverifiable` | 라벨과 명세의 언어가 달라 기계 판정 불가 |
| `e2e-only` | E2E 에만 태그가 있어 게이트(jest)가 보지 못함 — 정확 |

**게이트로 만들지 않았다.** 유사도는 휴리스틱이므로 임계값으로 통과/탈락을 가르면
근거 없는 상수가 하나 더 생긴다(TS-008 의 `EVAL_WEIGHTS` 교훈). 두 문자열과 수치를
함께 출력해 사람이 판단한다.

설계를 네 번 고쳐서야 오탐 0 이 되었고, 그 과정 자체가 교훈이다.

1. 줄 전체에서 라벨을 긁었더니 구분선(`─`)과 괄호가 라벨로 잡혔고,
   그 쓰레기 라벨이 "겹침 100%"로 계산되어 **진짜 불일치를 가렸다**.
   → 라벨은 **문자열 리터럴**에서만 얻는다.
2. 콜론(`F-004:`)만 믿었더니 `test('… 표시 (F-020)')` 처럼 ID 가 뒤에 오는 형태를 놓쳤다.
   → 리터럴 전체를 라벨로 보고 ID 토큰만 제거한다.
3. 참조마다 판정했더니 **14건 중 11건이 오탐**이었다 — 개별 `test` 이름은 단계를
   서술하므로 기능 설명과 겹치지 않는 것이 정상이다.
   → `describe` 라벨만, 단계 태그가 없는 것만 평가한다.
4. 줄 전체를 스캔하니 **주석에 적은 ID**("ARIA 는 F-026 이 다룬다")까지 태그로 집계됐다.
   → 주석은 증거가 아니다. 리터럴 안의 ID 만 수집한다.

판정은 **기능 단위**로 한다 — 그 기능을 올바로 지칭하는 `describe` 가 하나라도 있으면
나머지는 하위 측면을 가리키는 정상적인 이름이다.

### 피험체 — 판단 기준을 세우고 선택적으로 교정
기준: **"이 실패가 하네스에 교훈을 주는가"**

| 실패 | 판정 | 조치 |
|---|---|---|
| 라벨 오기 3건 | 측정 도구 오류 | 고침 — 명세에 대응 기능이 없는 테스트에서 ID 제거, `F-020`→`F-002.5` |
| 제목 단정 | 명세에 없는 것을 단정 | 고침 — 실제 값(`Harness Web Target`)으로 교정 |
| `data-testid` 요구 | 취약한 셀렉터 | 고침 — 역할 기반 질의로. **앱에 훅을 추가하지 않았다** |
| 키보드 포커스 | 테스트가 F-003 과 모순 | 고침 — 유효 입력 후 포커스 초기화하고 탐색 검증 |
| **F-001 / F-004 E2E** | **앱의 인증 설계 결함** | **고치지 않음** — `test.fixme` + 사유 7줄 기록 |

F-001·F-004 의 E2E 는 같은 원인에 막힌다. 앱은 토큰이 디코드 가능한 JWT 여야 하는데
테스트는 `'mock-token'` 을 넣고, 앱은 디코드 실패 시 사용자를 null 로 만든다.
그 뒤에 깔린 설계 결함 네 개:

1. `LoginForm` 이 서버가 준 `user` 객체를 버리고 토큰만 저장한다
2. `AuthContext` 가 클라이언트에서 디코드한 `isAdmin` 을 신뢰한다 (localStorage 위조 가능)
3. `AuthContext.login()` 은 **죽은 코드**다 — 하드코딩 자격증명 + `'dummy-signature'`
4. 로그인 후 `window.location.href` 로 전체 리로드

고치려면 인증 흐름 전체를 재설계해야 하고, **하네스에는 아무 교훈이 없다.**
그래서 테스트를 앱에 맞춰 약화시키지도, 앱을 고치지도 않고 `test.fixme` 로 **신호를 보존**했다.
F-004 의 jest 증거(태그 4건)는 `useAuth` 를 모킹하므로 영향받지 않는다.

## Prevention
- **ID 가 맞는 것과 라벨이 맞는 것은 다른 문제다.** 증거 규약을 도입하면
  그 규약 자체를 검사하는 장치가 필요하다.
- 휴리스틱은 **게이트가 아니라 보고기**로 둘 것. 임계값으로 자동 차단하면
  근거 없는 상수가 늘어난다.
- 태그 수집은 **문자열 리터럴 안으로** 제한할 것. 주석의 ID 는 증거가 아니다.
- 라벨 검증은 `describe` 단위로 할 것. 개별 케이스 이름은 단계를 서술하므로
  기능 설명과 겹치지 않는 것이 정상이다.
- **피험체의 결함에는 판단 기준이 필요하다**: "이 실패가 하네스에 교훈을 주는가".
  주지 않으면 고치지 말고 `test.fixme` + 사유로 신호를 보존한다 —
  테스트를 앱에 맞춰 약화시키는 것이 가장 나쁜 선택이다.
- 명세에 대응 기능이 없는 품질 측정(성능·접근성)에는 **기능 ID 를 붙이지 말 것.**
  붙이면 그 기능이 검증된 것처럼 보인다.
