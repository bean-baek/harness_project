## Symptoms
TS-008 이 남긴 주관성을 실제로 공격해봤다. 아무것도 실행하지 않는 테스트를 심었다.

```tsx
describe('F-006: 사용자가 자신의 프로필 정보를 수정할 수 있다', () => {
  test('F-006.1: 이름을 변경한다', () => {
    expect(true).toBe(true);
  });
});
```

게이트는 **통과시켰다.**

```
[완료] '사용자가 자신의 프로필 정보를...': False → True
       (증거: suite 52/52 passed | tagged 1 passed | steps 1/5 covered)
```

구현 코드를 한 줄도 쓰지 않고 `passes: true` 와 증거 기록을 얻었다.
게이트는 **이름만** 보기 때문이다.

## Root cause
- **TS-008 의 기준은 필요조건일 뿐이었다.** "기능 ID 를 인용하는 통과 테스트"는
  테스트가 **무엇을 하는지** 묻지 않는다. 이름이 맞고 통과하면 증거가 된다.
- 이것은 사용자가 제기했던 순환("임의로 만든 테스트에 의해 바뀌는 게 맞나")의
  가장 직접적인 형태다. TS-013 이 통합 수준에서 같은 문제를 드러냈고,
  이번은 단위 수준에서 드러났다.

## Fix — 두 층으로 나눴다
비용 구조가 설계를 결정했다. 커버리지는 약 9초, 돌연변이는 변이당 타입검사+테스트로
분 단위다. 그래서 **정확하고 빠른 것만 게이트에 담고, 느리고 깊은 것은 측정 명령**으로 뒀다.

### 1층 — 커버리지 요구 (게이트, 정확)
`harness/verify.py` 의 `coverage_for_feature()`:
해당 기능의 태그 테스트만 실행해 **비(非)테스트 소스를 몇 statement 덮는지** 센다.
0이면 거부한다. 휴리스틱이 아니라 사실 판정이다.

**함정 1 — 호출 위치.** 기능별 커버리지는 jest 를 한 번 더 돌린다. `verify_feature`
안에 넣으면 `audit`/`report` 가 멈춘다(`discrimination_report` 는 75기능 × 3수준 =
225회 측정이 된다). 그래서 **플래그를 쓰는 순간(`apply_flag`)에만** 수행한다 — 기능당 한 번.

**함정 2 — `--testNamePattern` 만으로는 오염된다.** 이 옵션은 테스트 *실행*만 건너뛰고
테스트 파일은 **전부 import** 한다. 다른 파일들의 모듈 수준 import 가 커버리지에 섞여,
위의 공허한 테스트가 **42 statements 를 덮은 것으로 집계**됐다(실측). 처음 구현이
그래서 공허한 증거를 통과시켰다. `harness/tags.py` 로 태그가 있는 파일을 찾아
**그 파일만 jest 인자로 넘겨** 범위를 좁혀 해결했다.

**함정 3 — 커버리지 임계.** 부분 실행이므로 전역 임계(80%)에 반드시 걸린다.
`--coverageThreshold={}` 로 끄지 않으면 측정이 실패한 것처럼 보인다(TS-012 와 같은 혼동).

### 2층 — 돌연변이 측정 (명령, 깊음)
`harness/mutate.py` + `cli mutate <기능>`:
증거가 실제로 실행하는 파일에 구문을 유지하는 변이를 넣고 태그 테스트가 실패하는지 본다.

- 변이 규칙 6종(비교 반전, 논리 반전, 경계 이동, 불리언 반전, 조건 무력화)
- 적용 후 **`tsc --noEmit` 으로 유효성 확인** — 깨진 변이를 "잡았다"로 세지 않는다(invalid 폐기)
- 성공·실패·예외와 무관하게 `finally` 에서 **원본 복원**
- 점수 = 잡음 / (잡음 + 생존), invalid 는 분모에서 제외

### 점수 50% 의 해석 (중요)
생존 2건이 **전부 `LoginForm.tsx`** 였다. F-005 의 증거가 그 파일을 *스쳐 지나가지만*
소유하지는 않는다(LoginForm 의 검증 로직은 F-001~003 의 책임이다).
변이 대상을 커버리지로 고르므로 **다른 기능이 소유한 파일이 섞인다.**

그래서 보고서가 생존을 두 갈래로 나눠 출력한다 — 소유 파일의 생존은 "증거의 진짜 구멍",
스쳐 지나간 파일의 생존은 "그 파일을 소유한 기능에서 다시 확인할 일".
**오해를 부르는 수치는 없는 수치보다 나쁘다**는 판단이다.

## Prevention
- **증거 기준은 층으로 쌓을 것.** 이름(TS-008) → 소스 실행(이번) → 결함 감지(돌연변이).
  각 층은 앞 층의 구멍을 메우고, 뒤 층은 더 비싸다.
- **비싼 검사는 쓰기 경로에만 둘 것.** 읽기(`audit`/`report`)는 대량 반복되므로
  거기에 넣으면 도구가 멈춘다.
- `--testNamePattern` 은 **파일 로딩을 막지 않는다.** 커버리지를 기능별로 측정하려면
  파일 범위까지 좁혀야 한다. 그러지 않으면 공허한 테스트가 남의 import 를 제 공으로 가져간다.
- 부분 실행에는 **커버리지 임계를 끌 것.** 끄지 않으면 측정 실패와 임계 미달이 구분되지 않는다.
- 파일을 변형하는 도구는 **`finally` 에서 복원하고, 복원을 테스트로 고정할 것.**
- 돌연변이 점수를 **"테스트 품질"로 읽지 말 것.** 변이 대상 선정 방식에 따라
  남의 코드가 섞인다. 수치와 함께 그 한계를 출력하는 것이 정직하다.
