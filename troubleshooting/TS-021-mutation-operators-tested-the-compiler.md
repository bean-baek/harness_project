## Symptoms
돌연변이 측정을 게이트로 올리려고 **먼저 비용을 실측**했다. 그 과정에서 비용 가정과
연산자 정확성이 둘 다 틀렸다는 것이 드러났다.

### 1. 비용 가정이 틀렸다 — 10배 차이

처음 측정: tsc 10.79초, 범위 jest 18.40초 → 변이당 29초, F-005 6건에 181초.
**콜드 캐시였다.** 같은 명령을 두 번 돌려 웜 값을 재니:

| 단계 | 콜드 | 웜 |
|---|---|---|
| `tsc --noEmit` | 10.79초 | **1.86초** |
| 범위 jest (2파일) | 18.40초 | **2.75초** |

"2분이라 게이트에 못 넣는다"는 판단의 근거가 콜드 측정이었다. 웜에서는 변이당 4.6초다.
`--maxWorkers=1`·`--silent`·`--bail`·`--cache` 는 **아무 효과도 없었다**(2.69~2.78초).
jest 의 2.75초 중 2.51초는 패턴이 하나도 맞지 않을 때도 드는 **순수 시작·변환 비용**이고
실제 테스트 실행은 0.24초다. 즉 줄일 여지가 없다.

### 2. 변이 연산자가 구문을 파괴했다

`mutate.py` 의 주석은 "전부 **구문을 유지하는** 치환이다"라고 적혀 있었다. 아니었다.

```
원본: export const ProtectedRoute: React.FC<ProtectedRouteProps> = ({
변이: export const ProtectedRoute: React.FC<ProtectedRouteProps>= = ({
```

`>` → `>=` 규칙이 **제네릭의 닫는 꺾쇠**를 치환했다. 대상 앱 전수 조사:

| 규칙 | 매칭 | 진짜 대상 |
|---|---|---|
| `>` → `>=` | **190곳** | **3곳** (JSX 108곳, 제네릭 32곳 포함) |
| `if (X)` → `if (false)` | 26곳 | 21곳 (**5곳이 중첩 괄호로 깨짐**) |

```
if (!emailRegex.test(email)) return x;   →   if (false)) return x;
```

`[^)]{1,80}` 는 첫 `)` 에서 멈추므로 괄호가 남는다.

**변이가 테스트를 시험하는 게 아니라 컴파일러를 시험하고 있었다.** 그리고 그 사실은
'폐기(invalid) 2건'이라는 집계에 가려졌다 — 폐기를 "변이가 유효하지 않았다"로 읽었지
"연산자가 잘못됐다"로 읽지 않았다. F-005 의 변이 예산 6건 중 2건이 그렇게 낭비됐다.

## Root cause
- **정규식으로 TypeScript 의 `>` 를 다룰 수 없다.** `>` 는 비교·제네릭 닫기·JSX 태그
  닫기·화살표(`=>`)에 모두 쓰인다. 이전 패턴 `(?<![<>=!])>(?![=>])` 는 화살표만
  제외했고 제네릭과 JSX 를 그대로 쳤다.
- **정규식으로 괄호 균형을 맞출 수 없다.** 중첩 괄호는 문자를 세야 한다.
- **'폐기' 집계가 연산자 결함을 가렸다.** 측정값에 "도구 자신의 결함"을 담는 칸이
  없으면 그 결함은 데이터처럼 보인다.

## Fix
### 1. 연산자 교정
```python
# 공백을 양쪽에 요구한다 — `a > b` 만 남는다.
# `=>` 는 `>` 앞이 `=` 이므로 자동 제외된다.
("경계 이동 (a > b → a >= b)", r"(?<=\s)>(?=\s)", ">="),
```
190곳 → **3곳**. 남은 3곳은 전부 진짜 비교였다
(`unreadCount > 0`, `payload.exp * 1000 > Date.now()`, `prev.completed > current.completed`).

조건 무력화는 정규식을 버리고 `neutralize_condition()` 으로 옮겼다 — `(` 부터
**문자를 세어** 짝이 맞는 `)` 를 찾는다. 문자열 리터럴(`'`/`"`/`` ` ``) 안의 괄호는
건너뛰고, 조건이 여러 줄에 걸치면 `None` 을 돌려 **건드리지 않는다**.

### 2. 검사 순서로 비용 절감
jest 를 **먼저** 돌리고 tsc 는 **실패했을 때만** 돌린다.

> 통과한 변이는 컴파일된 것이므로 유효성을 다시 물을 필요가 없다.
> tsc 는 "테스트가 잡았다"와 "애초에 컴파일되지 않았다"를 구분할 때만 필요하다.

생존 변이당 1.9초 절감. F-005 실측: **26.7초** (연산자 수정으로 폐기가 0이 된 효과 포함).

### 3. 게이트로 승격 — `REQUIRE_MUTATION_EVIDENCE`
기준은 **"유효한 변이 1개 이상을 잡는다"**. TS-016 의 "소스 1줄 이상 실행"과 같은
모양의 **최솟값**이며 비율이 아니다.

비율(예: 80%)을 쓰지 않는 이유: 변이 대상을 커버리지로 고르므로 다른 기능이 소유한
파일이 섞인다(F-005 의 생존 3건은 전부 `LoginForm.tsx` 다). 그 혼합에 비율을 적용하면
`EVAL_WEIGHTS` 와 같은 **근거 없는 상수**가 된다. 점수와 귀속은 보고에 남긴다.

세 경우를 구분한다:

| 상황 | 처리 | 근거 |
|---|---|---|
| 도구가 돌지 않음 (`error`) | **거부** | 측정 실패는 통과가 아니다 (TS-016 의 규칙) |
| 유효한 변이 0건 | **거부하지 않고 기록** | 측정 **대상 부재**는 측정 **실패**와 다르다 |
| 잡음 0건 | **거부** | 소스를 실행하지만 단정하지 않는 증거다 |

두 번째가 TS-016 과 갈라지는 지점이다. 변이할 구문이 없는 코드(상수 선언만 있는 모듈 등)는
있을 수 있고 그것을 거부하면 거짓 거부가 된다. `measured: false` 와 사유를 기록해
사람이 볼 수 있게 한다.

**기본값은 false** — 기능당 약 27초이고 `mark` 가 11초에서 42초로 늘어난다(실측).
끈 상태에서도 `cli mutate <기능>` 으로 언제든 측정할 수 있다.

## Verification
`verification/repro_ts021.py` — **58/58 PASS**. jest·tsc 전부 스텁.

- 괄호 균형 13건 — 중첩·논리·깊은 중첩·`else if`·문자열 안 `)`·여러 줄(건너뜀)
- `>` 규칙 10건 — 비교 3종 포착, **제네릭·JSX 여닫기·화살표·중첩 제네릭·타입 단정 제외**
- **전수 구문 검사** — 대상 앱 소스 전체에 모든 규칙을 적용해 불변식 위반 0건
- 검사 순서 7건 — 생존만 나오면 **tsc 호출 0회**, 실패 시에만 tsc, 폐기는 분모 제외
- 게이트 14건 — 잡음 0 거부 / 잡음 1 통과+기록 / 도구 오류 거부 /
  변이 대상 부재는 기록만 / 끈 상태에서 측정 자체를 건너뜀
- 실제 레포 — 기록된 측정값이 기준을 만족하고 **폐기 0건**

### 불변식 정의에서 두 번 틀렸다 (기록)
전수 검사의 기준을 처음엔 "괄호·꺾쇠 **개수** 동일"로 썼다. 6건이 걸렸는데 전부 오탐이었다 —
`if (!re.test(email))` → `if (false)` 는 개수가 2→1 로 줄지만 **균형은 유지**된다.
하위 식을 통째로 지웠으니 당연하다. 올바른 불변식은 **순증감(delta) 동일**이다.

고치니 2건이 남았다. `if (password.length < 8)` → `if (false)` 가 `<` 를 지운 것이었다.
이것도 오탐 — 그 `<` 는 제네릭이 아니라 **비교 연산자**이고 조건을 통째로 지우는 것이
규칙의 의도다. 꺾쇠 검사는 **치환 규칙에만** 적용해야 한다.

기준 자체를 두 번 고쳐야 했다는 것을 남겨 둔다. 검사기를 만들 때 **무엇이 불변인지**를
먼저 정확히 정의하지 않으면 오탐으로 자기 시간을 쓴다.

### 회귀가 내 실수를 잡았다
TS-016 이 5건 실패했다. 두 원인이 섞여 있었다.

1. **내가 만든 버그** — `verification["summary"] += ...` 줄이 내 편집으로 돌연변이
   블록의 `else` 안으로 밀려 들어가, 돌연변이를 측정했을 때만 요약이 갱신되게 됐다.
   커버리지 블록으로 되돌렸다.
2. **스텁 대본이 옛 호출 순서를 전제** — `type_results`/`fail_results` 가
   "tsc 먼저" 순서로 쓰여 있었다. 동작이 아니라 순서가 바뀐 것이므로 대본을 새 순서로
   갱신했다(그 이유를 주석에 적었다).

전체 회귀 **549건**(기존 491 + TS-021 58) 통과, 자기 감사 0/0/0, 게이트 6/6.

## Prevention
- **최적화 전에 웜/콜드를 구분해 측정할 것.** 콜드 한 번으로 "느리다"를 결론내면
  10배 틀린 수치로 설계를 결정한다. 같은 명령을 두 번 돌리는 데 드는 비용이 가장 싸다.
- **정규식으로 언어 구문을 치환하지 말 것.** `>` 는 TS 에서 네 가지로 쓰이고 괄호는
  중첩된다. 치환이 **어디에 걸리는지 전수 조사**한 뒤에만 쓴다 —
  190곳 중 3곳이라는 사실은 한 번 세어보면 바로 나왔다.
- **도구 자신의 결함을 측정값에 섞지 말 것.** '폐기'가 "변이가 유효하지 않다"와
  "연산자가 잘못됐다"를 함께 담으면 후자가 데이터로 위장된다.
- **검사 순서가 비용이다.** 싼 검사를 먼저 돌려 비싼 검사를 건너뛸 수 있는지 보라.
- **불변식을 먼저 정확히 정의할 것.** "개수 동일"과 "순증감 동일"은 다르고,
  "모든 규칙"과 "치환 규칙만"은 다르다. 둘 다 틀려서 두 번 고쳤다.
- **측정 대상 부재와 측정 실패를 구분할 것.** 전자를 거부하면 거짓 거부가 되고,
  후자를 통과시키면 TS-016 의 실수를 반복한다.
