## Symptoms

F-005 의 돌연변이 점수가 이틀 동안 네 번 다르게 발표됐다 — 50% → 40% → 33% → 50%.
[TS-024](TS-024-published-numbers-go-stale.md) 는 이것을 **발표 과정의 드리프트**로
진단하고 생성 파일로 처방했다. 그 진단은 절반만 맞았다.

**네 수치가 전부 틀렸다.** 측정 자체에 결함이 있었다.

```
수정 후 F-005:  잡음 4 / 생존 0 / 폐기 1 / 타입이 잡음 1 / 명세 범위 밖 3
               점수 100%   (닿는 자리에서만)
               도달률 21줄 중 5줄 (24%)
```

생존이 **0건**이다. 이전의 "생존 2~10건"은 전부 **증거가 지나가지 않는 줄**에
심은 결함이었다.

## Root cause

### 커버리지는 파일을 고르는 데만 쓰였다

```python
@dataclass
class Coverage:
    per_file: dict[str, int]      # ← 개수뿐이다
```

`per_file` 은 "이 파일이 13줄 실행됐다"까지만 안다. 그 13줄이 **어느 줄인지**는
담지 않는다. 그런데 변이는 **줄 단위로** 들어간다.

```
변이 대상 파일 선정   커버리지 사용  ✓
변이 대상 줄 선정     커버리지 없음  ✗   ← 여기
```

그래서 13줄 실행된 파일의 **미실행 줄**에 결함이 심어졌다. 그 변이를 지나가는
테스트가 없으므로 **생존이 보장**된다. 그리고 생존은 점수의 분모에 들어간다.

```
점수 = 잡음 / (잡음 + 생존)
                     ↑ 생존이 보장된 변이가 섞인다 → 점수가 틀린 값으로 낮아진다
```

실측 — `LoginForm.tsx`:

| | |
|---|---|
| 변이 후보 | 18곳 |
| 그중 실행되는 줄 | **2곳** |
| 넣으면 생존이 보장되는 자리 | **16곳** |

### 이것은 TS-022 의 부작용이다

TS-022 이전에는 규칙당 `lines[0]` 만 썼다. 파일 앞머리에 쏠려 있었고, 우연히
그쪽이 주로 실행되는 줄이었다. TS-022 가 표본을 **고르게 퍼뜨린** 뒤로 미실행 줄까지
균등하게 뽑히기 시작했다. 점수가 50% → 40% → 33% 로 내려간 것이 그 궤적이다.

TS-022 는 **닿는 범위**를 넓혔고, "닿아야 할 곳"과 "닿아도 의미 없는 곳"을
가르지 않았다. 수정이 새 결함을 만든 사례다.

### 가장 나쁜 부분 — 옳은 가설을 틀린 측정으로 기각했다

TS-022 의 조사 과정에 이 문장이 있다.

> 먼저 다른 가설을 세워 확인했고 **틀렸다**: "변이된 줄이 테스트가 실행하지 않는
> 줄이라서 생존이 당연한 것 아닌가". 줄 단위 커버리지를 재니 `LoginForm.tsx` 의
> 변이 지점 19곳이 **전부 실행되는 줄**이었다.

**가설이 옳았다.** 기각의 근거가 된 측정이 틀렸다.

무엇이 틀렸는가 — istanbul 의 statement 는 `start`~`end` **범위**를 갖는다.
함수 선언 statement 는 모듈 로드 때 실행되면서 **호출되지 않은 본문 전체**를
그 범위에 담는다. 범위를 '실행된 줄'로 간주하면:

```
LoginForm.tsx   범위 방식: 167줄이 '실행됨'  → 미실행 statement 54개 중 48개가 먹힌다
                시작줄 방식:   9줄이 '실행됨'  → 미실행과 겹치지 않는다
```

즉 **"19곳이 전부 실행되는 줄"은 측정 방법의 산물**이었다. 올바른 가설을 세웠고,
확인하려고 측정했고, 측정 방법이 틀려서 "아니다"라는 답을 받고 기각했다.

[TS-024](TS-024-published-numbers-go-stale.md) 가 적은 원인 1 — *"도구와 그 도구의
테스트를 같은 사람이 같은 이해로 만든다"* — 의 가장 선명한 형태다. 여기서는
**가설 검증용 일회성 측정**이 그 함정에 빠졌다. 회귀 스크립트로 고정되지 않은
측정은 아무도 다시 묻지 않는다.

## Fix

### 1. 런너 계약에 실행된 줄을 추가 — `Coverage.executed_lines`

```python
per_file: dict[str, int]                  # 기존 (호출자 전부 그대로 동작)
executed_lines: dict[str, set[int]]       # 신규
```

`lines_for(name)` 은 `None`(줄 지도를 모른다) 과 `set()`(실행된 줄이 없다) 을
**구분**한다. 전자를 후자로 취급하면 측정 실패가 조용히 '대상 없음'이 되고,
후자를 전자로 취급하면 미실행 파일에 변이를 넣는다 (TS-016 의 규칙).

### 2. istanbul 파싱 — **시작 줄만**, 그리고 `hit - miss`

```python
(hit if counts.get(sid, 0) else miss).add(loc["start"]["line"])
...
out[name] = hit - miss
```

범위를 쓰지 않는 근거는 위 실측이다. 같은 줄에 실행·미실행 statement 가 섞이면
제외한다 — 그 줄을 지나간 경로가 변이 지점을 지났다고 보장할 수 없다.
이 보수적 선택으로 줄어드는 후보는 `web_target` 기준 **0개**였다(실측). 비용 없이
안전한 쪽을 고를 수 있었다.

리포터를 추가해야 줄 지도가 나온다 — `json-summary` 는 개수만 준다.

```
jest     --coverageReporters=json            → coverage-final.json
vitest   --coverage.reporter=json            → 같은 파일
pytest   이미 executed_lines 를 직접 준다     → 환산 불필요
```

### 3. 변이 후보를 실행된 줄로 제한

```python
def _candidate_lines(text, pattern, executed=None):
    ...
    if executed is not None and i not in executed:
        continue
```

`None` 이면 필터하지 않는다 — 줄 지도를 못 얻은 상황을 '대상 없음'으로 바꾸지
않기 위해서다. 대신 그 파일을 `unmapped_files` 에 담아 **보고서가 그 사실을 적는다**:
*"이 파일은 미실행 줄 필터 없이 변이됐다. 점수가 과소평가일 수 있다."*

### 4. 점수와 **도달률**을 함께 발표한다

미실행 줄을 분모에서 빼면 점수가 올라간다. 무엇을 뺐는지 같은 자리에 적지 않으면
TS-024 의 '발표된 수치가 실제보다 좋아 보이는' 모양이 된다.

```
돌연변이 점수: 100%  (잡음 / (잡음+생존))
도달률: 변이 가능 지점 21줄 중 5줄에 증거가 닿는다 (24%)
        — 점수는 **닿는 자리에서만** 측정한 값이다
```

두 수치는 **다른 질문**의 답이다. 점수는 "증거가 닿는 곳에서 무는가", 도달률은
"증거가 어디까지 닿는가". 하나로 합치면 둘 다 잃는다.

단위를 맞춘다 — 둘 다 **줄 수**다. 한 줄에 규칙 두 개가 걸리면 변이는 2개지만
지점은 1곳이다. 처음 구현에서 변이 수와 줄 수를 섞어 "2개 + 1줄 = 3곳"으로 적고
있었고, 회귀 스크립트가 그것을 잡았다.

### 5. 게이트 — '구문이 없다' 와 '증거가 닿지 않는다' 를 가른다

`attempted == 0` 의 이유가 둘로 늘었다.

| 이유 | 기록되는 사유 | 판정 |
|---|---|---|
| 변이할 구문이 아예 없다 | "비교·논리·조건·불리언 없음" | 기록만 |
| 구문은 있는데 증거가 그 줄을 지나지 않는다 | "변이 가능한 구문은 N곳 있으나 증거가 하나도 지나가지 않습니다" | 기록만 |

둘을 같은 문구로 적으면 나중에 읽는 사람이 후자를 "상수만 있는 모듈"로 읽는다.
후자를 **거부하지 않는** 이유: 커버리지 게이트가 이미 '소스 1줄 이상 실행'을
요구했으므로 증거는 어딘가에 닿았고, 그 줄이 변이 가능한 구문이 아닐 수 있다 —
그것은 결함이 아니다.

통과 기록에도 `unreached_sites` 와 `unmapped_files` 를 함께 저장한다. 저장된
점수가 **무엇을 뺀 값인지** 없이 남으면 그것이 다음 TS-024 가 된다.

## Verification

```
python verification/repro_ts026.py
```

음성 대조를 포함한다 (verification 설계 규약 1) — **범위 방식이 틀렸다는 것**을
같은 입력으로 계산해 고정한다. 이 검사가 바로 TS-022 를 오판으로 이끈 측정 방법이다.

```
PASS  음성 대조: 범위를 쓰면 미실행 줄 6 이 섞인다
PASS  음성 대조: 범위를 쓰면 미실행 줄 7 도 섞인다
PASS  현재 구현은 그 둘을 넣지 않는다
```

`vanilla-js` 픽스처의 `neverCalled()` — TS-025 에서 이 결함을 고정할 목적으로 미리
심어 둔 함수 — 가 변이 대상에서 빠지는 것도 검사한다.

pytest 경로는 파싱을 `_parse_coverage` 로 떼어 **pytest 없이** 규약을 검증한다.
TS-025 가 기록한 "pytest 실행 미검증" 공백을 전부 메우지는 못하지만 파싱은 메운다.

## Lesson

**일회성 측정으로 가설을 기각하지 말 것.**

이 프로젝트의 측정 결함 네 건(TS-021·022·023·026)은 전부 `mutate.py` 에 있다.
TS-024 는 그 집중을 "돌연변이가 네 가지 독립 판단을 요구하기 때문"으로 설명했다.
TS-026 은 다섯 번째 판단을 추가한다 — **어디에 심을 것인가.**

| 판단 | 틀렸을 때 | 기록 |
|---|---|---|
| 무엇으로 바꿀 것인가 | 컴파일러를 시험한다 | TS-021 |
| 어디를 고를 것인가 (표본) | 같은 곳만 본다 | TS-022 |
| 생존이 무엇을 뜻하는가 | 명세 밖을 결함으로 읽는다 | TS-023 |
| **어디에 심을 것인가 (도달)** | **생존이 보장된 자리를 센다** | **TS-026** |

그리고 TS-022 의 조사 기록이 남아 있었기 때문에 — *"이 가설을 세웠고 이렇게
측정해서 기각했다"* — 1년 뒤가 아니라 오늘 정정할 수 있었다. **기각한 가설과
그 근거를 적어 두는 것**이 이 문서들의 값이다. 적지 않았다면 다시 세우지도
못했을 것이다.
