## Symptoms
TS-021 이 연산자의 **정확성**을 고쳤다. 남은 질문은 **도달 범위**였다 —
"점수 40%" 가 어느 표본에 근거한 수치인가. 측정했다.

### 1. 표본이 파일 앞머리에 고정돼 있었다

```
파일                      코드줄   변이지점   실제시도   도달률
LoginForm.tsx              156      19        3        16%
AuthContext.tsx            102       8        3        38%
ThemeContext.tsx            90       8        3        38%
합계                       758      59       23        39%
```

구현은 규칙마다 `lines[0]` **하나만** 썼다. 그래서 같은 줄이 영원히 반복된다.

```
LoginForm.tsx  조건 무력화  지점 9곳 → 32번 줄만 시도, [34, 39, 40, 55, 56]… 는 영원히 미검사
```

55·56번 줄은 `safeRedirectTarget` 의 오픈 리다이렉트 가드다 — **TS-011 의 수정**이다.
이 프로젝트가 가장 자랑하는 보안 수정이 **한 번도 변이 검사를 받지 않았다.**

먼저 다른 가설을 세워 확인했고 **틀렸다**: "변이된 줄이 테스트가 실행하지 않는 줄이라서
생존이 당연한 것 아닌가". 줄 단위 커버리지를 재니 `LoginForm.tsx` 의 변이 지점 19곳이
**전부 실행되는 줄**이었다. 점수는 정직했고 문제는 순수하게 표본 편향이었다.

### 2. 연산자가 배열 선언에 닿지 못했다

`routes.ts` 는 F-005 의 증거가 6줄 실행하는데 변이 지점이 **0곳**이다 —
배열 선언에는 비교·논리·조건·불리언이 없다. 그래서 **TS-013 의 버그 모양**을 주입할
수단이 아예 없었다: "명세가 보호를 요구하는 경로가 목록에서 사라진다".

손으로 실험했다. 보호 경로를 하나씩 지우고 **전체 스위트**를 돌렸다.

| 제거한 멤버 | 결과 | 스위트 |
|---|---|---|
| `/` | **생존** | 49 통과 / 0 실패 |
| `/dashboard` | 잡음 | 48 통과 / 1 실패 |
| `/profile` | **생존** | 49 통과 / 0 실패 |
| `/settings` | **생존** | 49 통과 / 0 실패 |

**4개 중 3개를 지워도 전부 통과한다.** 통과 수가 51에서 49로 줄 뿐이다 —
`test.each(PROTECTED_PATHS)` 는 목록이 줄면 **덜 돌기** 때문이다.
`/dashboard` 만 잡힌 이유는 `expect(PROTECTED_PATHS).toContain('/dashboard')` 로
이름이 박혀 있어서였다.

그 동안 **기존 사다리 네 칸이 전부 통과한다**:

| 칸 | 판정 |
|---|---|
| 태그 (TS-008) | 통과 — 태그 테스트는 그대로 있다 |
| 커버리지 (TS-016) | 통과 — 소스를 실행한다 |
| 독립성 (TS-020) | 통과 — `AppRoutes.test.tsx` 가 컬렉션을 import 한다 |
| 돌연변이 (TS-021) | 통과 — 연산자가 배열을 건드리지 못한다 |

## Root cause
- **예산과 편향을 혼동했다.** 예산을 제한하는 것은 비용상 정당하다. 문제는 제한하면서
  **항상 같은 곳**을 고른 것이다. `lines[0]` 은 샘플링이 아니라 고정이다.
- **연산자가 '연산자'만 봤다.** 치환 가능한 토큰(`===`, `&&`, `>`)을 찾는 설계여서
  **선언 자체**를 결함 주입 대상으로 보지 못했다. 그런데 이 프로젝트가 기록한
  가장 비싼 버그(TS-013)가 바로 선언의 결함이었다.

## Fix
### 1. `select_spread()` — 등간격 표본
후보를 **전부 모은 뒤** 예산만큼 고르게 뽑는다. 무작위가 아니라 등간격인 이유는
재현 가능해야 회귀로 고정할 수 있기 때문이다.

```
예산 3  → [0, 9, 18]        (이전: 앞머리 3곳)
예산 6  → [0, 4, 7, 11, 14, 18]
```

규칙별 루프도 없앴다 — 모든 규칙 × 모든 줄을 하나의 후보 목록으로 합쳐 줄 번호로
정렬한 뒤 퍼뜨린다. 그래서 예산이 작아도 파일 전체에 걸쳐 분포한다.

### 2. `drop_member()` — 컬렉션 멤버 제거 연산자
`independence.declared_collections()` 가 이미 찾아 둔 "앱이 선언한 단일 출처 컬렉션"을
재사용한다. 두 모듈이 합쳐져 **선언의 결함**을 주입한다.

선언 범위 안에서만 지운다 — 같은 문자열이 주석이나 다른 변수에 있어도 건드리지 않는다.
마지막 멤버를 지울 때 앞 쉼표를 걷어내 `['a',]` 가 되지 않게 한다.

### 3. `types` 상태 — 타입이 잡은 것을 '폐기'로 묻지 않는다
`/dashboard` 제거는 처음에 **폐기(invalid)** 로 분류됐다. 그런데 `drop_member` 는
배열 리터럴을 유지하므로 **구문은 구성상 유효하다.** tsc 가 실패한 이유는
`PAGE_BY_PATH: Record<ProtectedPath, …>` 가 목록과 소비처를 타입으로 묶어 두었기
때문이다 — 즉 **타입 수준의 결함 감지**다.

증거 점수의 **분자에는 넣지 않는다**: 잡은 것은 테스트가 아니고, 게이트가 묻는 것은
증거의 품질이다. 그러나 '폐기'로 묻어버리면 **구조적 보호가 있다는 사실**이 사라진다.
그래서 별도 상태로 센다.

### 4. 표본 크기를 보고한다
`sites`(후보 총수)와 `attempted`(시도 수)를 결과에 담고 보고서에 출력한다.
이것이 없으면 "점수 33%" 가 몇 개 표본에 근거한 수치인지 알 수 없다.
`cli mutate --max-per-file N --max-collection N` 으로 예산을 늘릴 수 있다.

## Prevention
- **예산 제한과 표본 편향을 분리할 것.** 비용 때문에 전수를 못 하는 것은 정당하지만,
  제한하면서 **항상 같은 곳**을 고르면 그 나머지는 영원히 검사되지 않는다.
  `lines[0]` 은 샘플링이 아니다.
- **표본 크기를 수치와 함께 출력할 것.** "40%" 가 3표본인지 100표본인지 모르면
  그 수치로 판단할 수 없다. 측정값에는 **분모의 출처**가 붙어야 한다.
- **결함을 '연산자'에서만 찾지 말 것.** 선언·목록·설정도 결함이 들어가는 자리이고,
  이 프로젝트에서 가장 비싼 버그(TS-013)가 바로 선언의 결함이었다.
- **"잡혔다"의 주체를 구분할 것.** 테스트가 잡은 것과 타입 검사가 잡은 것은 다르다.
  섞으면 증거 품질이 과대평가되고, '폐기'로 묻으면 구조적 보호가 보이지 않는다.
- **가설을 먼저 반증할 것.** "생존은 미실행 줄 때문"이라는 설명이 그럴듯했지만
  줄 커버리지를 재니 틀렸다. 그 측정을 건너뛰었다면 엉뚱한 것을 고쳤을 것이다.
- **목록을 순회하는 테스트는 목록이 줄면 조용해진다.** `test.each(LIST)` 는
  멤버가 사라지면 **덜 돌 뿐** 실패하지 않는다. 목록의 **크기나 멤버 자체**를
  단정하는 테스트가 따로 필요하다.
