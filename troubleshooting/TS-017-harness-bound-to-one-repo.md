## Symptoms
TS-005~TS-016 이 잡아낸 실패 양식 16종은 생태계와 무관하다 — 자기 채점, 공허한 증거,
태그 오귀속, 측정 고아화는 jest 든 pytest 든 똑같이 일어난다. 그런데 **그 양식을
집행하는 코드는 이 레포 한 곳에만 붙었다.** 함수 단위로 측정했다:

| 모듈 | 전체 | 런너·경로에 묶인 양 |
|---|---|---|
| `cli.py` | 434줄 | 0% |
| `metrics.py` | 501줄 | 0% |
| `tags.py` | 310줄 | 0% (상수 4개) |
| `mutate.py` | 266줄 | 8.6% |
| `verify.py` | 609줄 | 33% |
| **합계** | **2,120줄** | **10.6% (224줄)** |

즉 판정 **정책**은 처음부터 생태계 중립이었고, `subprocess` 호출 네 군데와
상수 네 개만 jest·`web_target`·`.test.tsx`·`F-\d{3}` 에 박혀 있었다.

두 번째 증상이 더 컸다. 사용자가 물었다 — *"테스트라는 게 뭐야? 내가 테스트를
정의해야 한다는 거야?"* 하네스는 `features.json`(의도) 없이는 아무 기능도 통과시키지
못하는데, **의도를 전부 사람이 적어야 한다고 암묵적으로 전제**하고 있었다.
그 전제는 과했다. 검사할 수 있는 것 중 상당 부분은 의도를 몰라도 판정된다.

## Root cause
1. **설정이 코드에 있었다.** 네 가지(런너·대상 경로·테스트 접미사·ID 형식)가
   선언이 아니라 상수였다. 바꾸려면 코드를 고쳐야 했고, 그래서 아무도 안 바꿨다.
2. **순환과 불변식을 구분하지 않았다.** TS-013 이후 "코드에서 명세를 뽑으면 순환"이라는
   결론만 남고, **그 결론이 적용되지 않는 경우**를 분리하지 않았다.

   - 순환   — 구현 A 를 읽어 명세를 쓰고 구현 A 를 검사한다. 항상 통과한다. 무의미.
   - 불변식 — 선언 D 와 구현 I 의 **일치**를 검사한다. 둘 중 하나가 틀리면 잡힌다.

   `routes.ts` 의 `PROTECTED_PATHS` 와 `App.tsx` 의 라우트 등록은 **서로 다른 두 지점**
   이다. "선언된 경로가 모두 등록되는가"는 코드에서 추출했지만 순환이 아니다 —
   판정에 "무엇이 보호되어야 하는가"라는 의도가 필요하지 않다.

## Fix — 세 모듈
### `harness/project.py` — 설정 외부화 + 검수
`.harness.json` 이 런너·대상·명세 경로·ID 형식·접미사·소스 디렉터리·정적 검사 커맨드를
선언한다. 선언이 없으면 **검수해서 추론하고 근거를 함께 출력한다** (`Finding`).
출처를 `선언 / 실측 / 기본값` 세 가지로 표시하는 이유: "자동 감지했습니다"만 출력하면
틀렸을 때 사용자가 알 수 없다 (TS-009 가 같은 문제였다).

**기본값은 외부화 이전의 하드코딩과 같은 값이다.** 따라서 `.harness.json` 을 추가하지
않은 프로젝트의 동작은 변하지 않는다 — 기존 236개 검증이 전부 그대로 통과하는 것으로
확인했다.

**검수는 판정 경로에서 하지 않는다.** `config_for()` 는 파일만 읽고 추론하지 않는다.
자동 추론은 `cli init` / `cli inspect` 처럼 사람이 결과를 눈으로 보는 경로에서만 돈다.
판정 경로에서 조용히 추론하면 무엇을 근거로 거부·통과했는지 재현할 수 없다.

### `harness/runner.py` — 생태계에 묶인 전부
네 연산만 런너에게 묻는다: `run_all` / `results` / `coverage` / `typechecks`
(+ 돌연변이용 `run_scoped`). jest·vitest·pytest 구현을 넣었다.
다른 생태계는 **이 파일에만** 클래스를 추가하면 된다.

모든 연산은 `(값, 진단)` 을 돌려주고 값이 `None` 이면 **측정 실패**다.
측정 실패는 통과가 아니다 (TS-016) — 게이트가 거부로 처리한다.

함정들:
- **vitest 는 `run` 서브커맨드가 없으면 watch 모드로 멈춘다.** 이것 하나로 CI 가
  타임아웃까지 매달린다. jest 와 가장 다른 지점이다.
- vitest 는 `--root`(jest 는 `--rootDir`), `--reporter=json`(jest 는 `--json`),
  `--coverage.reporter=`(jest 는 `--coverageReporters=`) 를 쓴다.
  커버리지 임계를 끄는 방법도 다르다 — jest 는 `--coverageThreshold={}` 한 방이지만
  vitest 는 `--coverage.thresholds.<metric>=0` 을 네 번 넘겨야 한다.
- pytest 는 **내장 junit-xml** 로 결과를 읽는다. `pytest-json-report` 는 서드파티이고
  남의 레포에 설치를 요구할 수 없다. 커버리지는 `pytest-cov` 가 필요하며, 없으면
  측정 실패를 반환한다 (게이트가 거부한다 — 측정 못 한 것을 통과시키지 않는다).

### `harness/inspect.py` — 의도 없이 판정되는 것
두 갈래로 나눠 보고한다.

**자동 판정 (`auto=True`)** — 선언과 구현의 일치. 지금 바로 ok/violated 가 나온다.
- `dead-script` — npm 스크립트가 참조하는 바이너리가 의존성에 있는가 (TS-012 재현)
- `route-completeness` — 선언된 경로 목록이 라우터에서 소비되는가
- `untested-source` — 어떤 테스트도 import 하지 않는 소스 (커버리지 0 확정)
- `unreferenced-export` — export 됐지만 아무도 참조하지 않는 심볼

**의도 필요 (`auto=False`)** — 후보로만 제시한다.
- `form-rules` — 폼이 있다. 무엇을 거부해야 하는가는 코드에 없다.
- `error-path` — `await` 가 있고 오류 분기가 없다. 실패 시 무엇을 보일지는 의도다.

**명세 초안은 `features.draft.json` 에만 쓴다.** `features.json` 에 바로 넣으면 하네스가
자기가 코드에서 뽑은 명세로 그 코드를 검사하게 된다 — 정확히 순환이다. 각 항목에
`origin` 과 `needs_review` 를 박아 출처를 지운 채 섞이지 않게 한다.

## 실측에서 잡은 오탐 3건 (전부 수정)
검수를 처음 돌렸을 때 위반 4건이 나왔다. **2건이 오탐이었다.**
이 프로젝트는 돌연변이 점수에서 이미 같은 결론에 도달했다 —
**오해를 부르는 수치는 없는 수치보다 나쁘다.**

1. **"PROTECTED_PATHS 의 /dashboard, /profile, /settings 가 등록되지 않았다"**
   → 거짓. `App.tsx` 가 `PROTECTED_PATHS.map()` 으로 **생성**한다. 정규식은 리터럴
   `path="..."` 만 봤다. 수정: 선언 목록을 순회하는 코드(`.map`/`.forEach`/`for..of`)가
   있으면 **누락이 구조적으로 불가능**하므로 통과로 판정한다. 리터럴 등록과 변수 등록이
   섞여 있으면 **판정하지 않는다**(`needs-intent`).

2. **"/login 이 PROTECTED_PATHS 에 없다"**
   → 거짓. 로그인 페이지가 보호 대상이 아닌 것은 **설계**다. 역방향(등록 ⊆ 선언)에는
   근거가 없다 — 경로 목록은 보통 부분집합이다. 수정: 역방향 검사를 삭제했다.

3. **"ProtectedPath 가 참조되지 않는다"**
   → 거짓. `import { PROTECTED_PATHS, type ProtectedPath }` 의 인라인 `type` 한정자를
   떼지 않아 `"type ProtectedPath"` 라는 이름으로 등록됐다. 수정: 접두사를 제거한다.

추가로 **거짓 '실행 가능' 보고**를 잡았다. `launcher()` 의 npx 폴백은 설정 파일만 보고
커맨드를 만드는데, 패키지가 미설치면 `npx --no-install` 은 런타임에 실패한다.
vitest 미설치 Vite 프로젝트가 "실행 가능"으로 보고됐다. 수정: `available()` 이
`로컬 바이너리 있음` / `의존성에 선언됐으나 미설치` / `둘 다 아님` 셋을 구분한다.

## Prevention
- **규약은 선언으로 끌어낼 것.** 상수로 두면 바꿀 수 있다는 사실 자체가 숨는다.
  단, **기본값은 기존 하드코딩과 같게** 두어 기존 사용자의 동작을 바꾸지 않는다.
- **추론에는 근거를 붙일 것.** `선언/실측/기본값` 을 구분해 출력하면 사용자가
  무엇을 신뢰할지 판단할 수 있다. '기본값'은 "근거 없이 골랐다"는 자백이다.
- **판정 경로에서 추론하지 말 것.** 사람이 눈으로 보는 명령에서만 추론한다.
- **순환과 불변식을 구분할 것.** 코드에서 뽑은 검사가 전부 순환은 아니다.
  기준은 **두 지점이 서로 다른 곳에 있는가** 다. 같은 파일이면 순환, 다르면 불변식.
- **정적 검사에서 동적 생성을 만나면 판정을 보류할 것.** 리터럴만 보는 정규식은
  `.map()` 으로 생성된 것을 '누락'으로 본다. 모르는 것을 위반으로 보고하면
  사용자가 검사 전체를 믿지 않게 된다.
- **방향에 근거가 있는지 물을 것.** `선언 ⊆ 등록` 에는 근거가 있고
  `등록 ⊆ 선언` 에는 없다. 양방향을 기계적으로 검사하면 설계를 위반으로 보고한다.
- **'실행 가능'을 커맨드 생성 성공으로 판단하지 말 것.** 커맨드를 만들 수 있다는 것과
  그것이 돌아간다는 것은 다르다 (TS-012 의 죽은 npm 스크립트와 같은 구조의 착오다).
