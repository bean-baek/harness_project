## Symptoms
증거 사다리가 두 칸에서 멈춰 있었다.

```
이름 (TS-008)  →  소스 실행 (TS-016)  →  [빈칸]
```

빈 칸이 **돌연변이**라고 생각해 왔다. 틀렸다. 돌연변이는 **같은 채널의 깊이**를 재고,
TS-013 이 드러낸 것은 **채널의 독립성**이었다.

F-005 는 게이트를 통과했고 jest 51/51 이 녹색이었다. 그런데 실 브라우저에서 전혀
동작하지 않았다 — 앱에 `/dashboard` 라우트가 아예 없었다. 왜 못 잡았나:

```tsx
// ProtectedRoute.test.tsx — 테스트가 라우트를 직접 만들어 감쌌다
<Route path="/dashboard" element={<ProtectedRoute><Page/></ProtectedRoute>} />
```

테스트가 검증 대상의 구조를 공급하면 그 구조는 검증되지 않는다. "보호가 동작한다"만
확인하고 "앱이 그 경로를 선언했는가"는 묻지 않은 것이다.

**TS-013 의 수정은 정책이 아니었다.** `routes.ts` 를 단일 출처로 만들어 F-005 하나만
고쳤고, 다음 기능이 같은 실수를 반복하는 것을 막는 장치는 없었다. 게이트는 구조적으로
그것을 요구할 수도 없다 — 설계상 "게이트는 jest 만 실행한다"이므로 E2E 는 증거로
계수되지 않는다.

그 사이 `report` 의 **"회수(unmark) 횟수 = 게이트가 틀렸던 횟수"** 는 README 가 가장
중요한 지표라고 써 놓았는데 실제 데이터가 **0건**이었다. 유일하게 알려진 거짓 통과
(F-005)는 마크다운에만 있고 수치에는 없었다.

## Root cause
증거의 **출처**를 묻지 않았다. 게이트는 세 가지를 요구했다.

1. 기능 ID 를 인용하는 통과 테스트 (TS-008)
2. 그 테스트가 비(非)테스트 소스를 실행 (TS-016)
3. 스위트에 실패 0건 (TS-006)

셋 다 **단위 테스트 하나로 전부 만족된다.** 그리고 그 단위 테스트는 구현자가 썼다.
"구현자가 쓴 테스트가 구현자의 코드를 통과시킨다"는 순환의 가장 바깥 껍질이 남아 있었다.

## Fix — `harness/independence.py`
두 가지 **사실**을 세어 보고한다. 점수가 없다.

### 사실 1 — 자급(self-supplied) 판정
앱이 컬렉션을 선언했을 때(`export const PROTECTED_PATHS = [...]`), 그 기능의 태그
테스트가

- 그 컬렉션을 **import 해서 순회**하는가 → 앱의 선언을 읽는다
- 컬렉션의 멤버를 **문자열로 직접 적는가** → 자급

둘 다 `import 했는가 / 멤버 리터럴이 몇 개인가`라는 사실 질문이다. 실측 대비:

| 파일 | import | 리터럴 | 판정 |
|---|---|---|---|
| `AppRoutes.test.tsx` | `PROTECTED_PATHS` ✓ | `/dashboard` | 독립 (선언을 읽는다) |
| `ProtectedRoute.test.tsx` | 없음 | `/`, `/dashboard` | **자급** |

`AppRoutes.test.tsx` 에도 리터럴이 있지만 `expect(PROTECTED_PATHS).toContain('/dashboard')`
처럼 **import 한 컬렉션에 대해** 단정하므로 자급이 아니다. import 여부가 먼저다.

### 사실 2 — 채널 수
`unit_suffixes` / `e2e_suffixes` 로 이미 구분되는 두 채널 중 몇 개가 이 기능을
태그하는가. `tags.scan_tags` 를 재사용하므로 런너를 돌리지 않는다.

### 등급은 두 사실을 **합치지 않고** 조합한다
| 등급 | 조건 |
|---|---|
| `cross-checked` | 채널 2개 |
| `single-channel` | 채널 1개, 컬렉션 재현 없음 |
| `self-supplied` | 컬렉션 재현 + 채널 1개 ← **TS-013 의 모양** |
| `no-evidence` | 태그 0건 |

합치지 않는 이유: '앱의 선언을 읽는다'와 '두 채널이 교차 검증한다'는 **다른 것**이다.
F-018 은 선언 문제가 없지만 채널이 하나뿐이고, F-005 는 채널이 둘이지만 자급 테스트가
섞여 있다. 하나의 점수로 뭉개면 둘 다 안 보인다.

## 실측에서 갈라낸 심각도 (오탐 방어)
첫 구현은 자급 2건을 **같은 등급으로** 보고했다. 확인해보니 성격이 전혀 달랐다.

```tsx
// ProtectedRoute.test.tsx — 구조를 공급한다
<Route path="/dashboard" .../>  <Route path="/" .../>        // 멤버 2개 열거

// UserMenu.test.tsx — 기대값을 단정한다
expect(mockNavigate).toHaveBeenCalledWith('/profile');        // 멤버 1개
```

후자는 라우트 테이블을 손으로 만드는 것이 아니다. 섞어서 보고하면 심각한 발견이
사소한 것에 묻히고, 결국 검사 전체를 믿지 않게 된다 (TS-017 에서 같은 결론에 도달했다 —
오해를 부르는 보고는 없는 보고보다 나쁘다). 그래서 둘로 나눴다.

| 심각도 | 조건 | 의미 |
|---|---|---|
| `enumerated` | 멤버 **2개 이상** | 컬렉션을 손으로 재현했다. 등급을 끌어내린다 |
| `hard-coded` | 멤버 **1개** | 기대값 단정. 약한 결합으로만 기록 |

경계를 2로 둔 근거: **'집합을 열거한다'와 '원소 하나를 지목한다'를 가르는 최솟값**이다.
점수가 아니라 개수이며, 어느 쪽이든 원본 리터럴을 함께 출력해 사람이 확인할 수 있다.

남는 구멍은 정직하게 말해 둔다 — `<Route path="/dashboard">` **하나만** 손으로 쓴
테스트는 `hard-coded` 로 분류되어 등급을 내리지 않는다. 그 경우를 잡으려면 리터럴의
**구문 위치**(`path=` 인가 `expect(...)` 인가)를 봐야 하고, 그것은 라우팅 전용
휴리스틱이 되어 생태계 중립성을 깬다. 지금은 보고에 남기고 수치를 쌓는다.

## 왜 게이트가 아닌가
`tags.py` 와 같은 자리에 둔다 — 보고만 하고 종료 코드는 항상 0 이다.

자급이 곧 결함은 아니다. 단위 테스트가 픽스처를 만드는 것은 정상이며, 문제는 그것이
**유일한 증거**일 때다. 통과/탈락으로 가르려면 "채널 몇 개면 충분한가"를 정해야 하고
그것은 `EVAL_WEIGHTS` / 75점과 같은 **근거 없는 상수**가 된다. 수치를 먼저 쌓는다.

## Prevention
- **증거는 '있는가'가 아니라 '어디서 왔는가'를 물을 것.** 구현자가 쓴 테스트가
  구현자의 코드를 통과시키는 것은 순환의 가장 바깥 껍질이다. 게이트의 세 요구조건은
  단위 테스트 하나로 전부 만족된다.
- **단일 사건의 수정을 정책으로 착각하지 말 것.** TS-013 은 `routes.ts` 로 F-005 를
  고쳤지만 같은 실수의 재발을 막지 못했다. 수정과 정책은 다른 작업이다.
- **채널 독립성과 검증 깊이를 구분할 것.** 돌연변이는 깊이를, 독립성은 출처를 잰다.
  둘 중 하나로 다른 하나를 대체할 수 없다.
- **같은 종류로 보이는 발견도 심각도가 다르면 나눌 것.** 구조 공급과 기대값 단정을
  섞어 보고하면 심각한 것이 사소한 것에 묻힌다.
- **기준이 되는 선언이 없으면 판정하지 말 것.** 컬렉션을 선언하지 않은 프로젝트에서는
  자급 판정의 근거가 없다. 추측하지 않고 "기준 없음"을 보고한다.
- **등급을 하나의 점수로 뭉개지 말 것.** 서로 다른 사실은 서로 다른 칸에 보고해야
  각각을 고칠 수 있다.
