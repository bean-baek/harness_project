## Symptoms
TS-006 의 증거 게이트는 `jest` 종료 코드만 봤다. 그래서 "스위트가 녹색"은 보장했지만
**그 스위트가 해당 기능을 검증한다는 보장은 전혀 없었다.** 실측 결과 플래그가 양방향으로 틀렸다.

| 기능 | 당시 플래그 | 실제 |
|---|---|---|
| F-015 경쟁 그룹 실시간 순위표 | `passes: true` | 순위표 **구현도 테스트도 전무**. 완전한 거짓 통과 |
| F-018 주간 완료 통계 차트 | `passes: false` | DashboardPage 테스트가 명세 **2단계 모두 검증** 중 |
| F-004 로그아웃 | `passes: true` (게이트 통과) | 검증 테스트는 실재했으나 **게이트는 그 사실을 모른 채** 승인 |

즉 TS-006 이 없앤 것은 "에이전트가 완료를 선언한다" 였고, 남은 것은
"스위트가 녹색이면 무엇이든 완료로 기록된다" 였다. 75개 기능 중 어느 것이든
LoginForm 테스트 27건의 녹색에 무임승차할 수 있었다.

## Root cause
- **D1 (명세–테스트 연결 부재)**: 게이트의 판정 입력이 `returncode` 단일 값이었다.
  기능 ID 와 테스트 사이에 아무 관계도 요구하지 않으므로, 판정은 "프로젝트 전체가
  건강한가" 였고 "이 기능이 동작하는가" 가 아니었다. 둘은 전혀 다른 질문이다.
- **D2 (명세의 steps 필드가 사용되지 않음)**: `features.json` 의 각 항목은
  `steps` 로 합격 조건을 이미 서술하고 있었는데, 하네스 어디서도 읽지 않았다.
  F-004 의 5단계 중 "인증 토큰 삭제" 가 검증되는지는 사람이 수동으로 확인해야만 알 수 있었다.
- **D3 (jest 설정 탐색이 프로젝트 밖으로 탈출)**: `--rootDir` 을 주지 않아 jest 가
  설정을 찾아 상위로 올라갔다. jest 가 설치되지 않은 빈 디렉터리에서 실행하면
  `<rootDir>` 이 **사용자 홈**으로 잡혀 `.vscode/extensions`, `.cursor/extensions` 전체를
  스캔하며 2분 타임아웃까지 멈추는 것을 실측했다. `npx` 폴백에 `--no-install` 이 없어
  패키지를 네트워크로 내려받으려 시도하는 경로도 있었다. 다중 프로젝트로 확장할 때
  남의 레포에서 이 두 동작은 치명적이다.

## 판정 기준의 근거 — 임의로 만든 규약이 아니다
이 수정의 핵심 질문은 "무엇을 객관적 기준으로 삼을 것인가" 였다.
가중치나 임계값(TS-006 시점의 `EVAL_WEIGHTS 40/30/20/10`, `75점`)은 경험적 근거가 없는
선언이므로 기준이 될 수 없다. 대신 **프로젝트가 이미 쓰고 있던 규약**을 채택했다.

`web_target/tests/LoginForm.test.tsx` 는 처음부터 이렇게 작성되어 있었다.

```
describe("F-001: 이메일/비밀번호 로그인", ...)
describe("F-002: 잘못된 자격증명 오류 처리", ...)
describe("F-003: 이메일 형식 유효성 검사", ...)
```

따라서 새 기준은 발명이 아니라 **기존 관행의 기계적 강제**다. 판정 대상은
"사람이 정한 점수" 가 아니라 **"명세 ID 를 인용하는 통과 테스트의 존재"** — 재현 가능하고,
반증 가능하며, 같은 입력에 같은 결과를 준다.

## Fix
- **[harness/verify.py](../harness/verify.py) (신설)** — 객관적 판정 계층
  - `verify_feature(project_root, feature, level)` — `jest --json` 의 구조화된 결과
    (`assertionResults[].fullName` / `status`)를 기능 ID 와 대조한다.
  - 판정 수준 3단계 (`config.EVIDENCE_LEVEL`, 기본 `feature`)
    - `suite` — 스위트 녹색만 (TS-006 동작, 하위 호환)
    - `feature` — 스위트 녹색 + 기능 ID 태그 통과 테스트 ≥ 1
    - `step` — 위 + 명세 `steps` 전부가 단계 태그로 덮일 때만 통과
  - **회귀 우선**: 스위트에 실패가 있으면 어떤 수준에서도 통과 불가.
  - 단계 커버리지는 수준과 무관하게 **항상 측정해 기록**한다 — 강제하지 않더라도
    어느 단계가 미검증인지는 남아야 한다.
  - 태그 경계: `F-004` 는 `F-0041` / `F-004b` / `XF-004` 에 오매칭되지 않는다.
    단계 태그는 `F-004.5` / `F-004-5` / `F-004#5` 를 허용하고 `F-004.50` 과 구분한다.
  - `audit_features()` — jest **1회 실행**으로 여러 기능을 일괄 재감사.
  - D3 방어: 두 실행 경로 모두 `--rootDir <project_root>` 고정,
    `npx` 폴백은 `--no-install` + **대상에 jest 설정이 실제로 있을 때만** 사용.
- **[harness/tools.py](../harness/tools.py)** — `update_features` 가 `verify_feature` 로 판정.
  거부 시 사유(회귀 / 태그 없음 / 태그 실패 / 단계 미검증)를 구분해 반환한다.
  통과 시 `verification` 에 판정 수준·스위트 통계·**근거 테스트 이름**·단계 커버리지를 기록.
  jest 실행 로직은 `verify` 로 이전하고, 쓰이지 않게 된 `_summarize_jest` /
  `_failing_tests` 는 제거했다.
- **[harness/prompts.py](../harness/prompts.py)** — 코더 절차 Step 3 에 태깅 규약을 명시하고
  도구 설명에 `update_features` 항목을 추가했다. 규약을 모르면 에이전트가 영구히
  게이트에 막히므로 이것은 선택이 아니다.
- **[config.py](../config.py)** — `EVIDENCE_LEVEL` (`HARNESS_EVIDENCE_LEVEL`).

## Prevention
- **"프로젝트가 건강하다" 와 "이 기능이 동작한다" 를 같은 질문으로 취급하지 말 것.**
  전체 스위트의 녹색은 회귀 부재의 증거이고, 기능 충족의 증거가 아니다.
- 완료 기록에는 **무엇을 근거로 통과시켰는지**(테스트 이름)를 함께 남길 것.
  이름이 남아 있으면 사람이 다시 돌려 반증할 수 있다.
- 기준을 새로 만들기 전에 **코드베이스가 이미 쓰는 규약**을 찾을 것.
  기존 관행을 강제하는 기준은 임의적이지 않고, 채택 비용도 거의 없다.
- 명세에 `steps` 가 있다면 그것을 읽어라. 사용되지 않는 합격 조건은 합격 조건이 아니다.
- 외부 도구를 남의 디렉터리에서 실행할 때는 **탐색 범위를 명시적으로 고정**할 것
  (`--rootDir`). 설정 자동 탐색은 프로젝트 경계를 넘어 사용자 홈까지 올라간다.
- 패키지 매니저 폴백에는 설치 억제 플래그를 붙일 것 (`npx --no-install`).
  검증 도구가 대상 환경을 변경해서는 안 된다.

## 남은 주관성 (정직한 한계)
이 수정이 없애지 **못한** 것:
- 명세(`description` / `steps`)를 사람이 쓴다는 사실. 명세가 틀리면 검증도 틀린다.
- 태그된 테스트가 실제로 그 단계를 **제대로** 검증하는지. 게이트는 이름과 통과 여부만 본다.
  빈 `expect(true).toBe(true)` 에 `F-004.5` 를 붙이면 통과한다.
- Evaluator(P-04)의 LLM 채점과 `EVAL_WEIGHTS` / `75점` 임계는 여전히 근거 없는 상수다.
  단, 이제 `features.json` 의 플래그는 그 점수에 의존하지 않는다 — 분리되었다.
