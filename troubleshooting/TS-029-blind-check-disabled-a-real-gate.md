## Symptoms

CI 에 이 줄이 있었다.

```yaml
- name: 프로젝트 검수 (객관 지표 — 현재는 보고만)
  run: python -m harness.cli inspect || true
```

`|| true` 는 **종료 코드를 버린다**는 뜻이다. 즉 검수는 돌지만 아무것도 막지 못했다.
주석이 그 이유를 적어 두고 있었다 — *"현재 대상 앱에 위반 2건이 있어 지금 차단하면
CI 가 영구히 빨간불이 된다."*

그 2건이 무엇인가:

```
[위반] 모든 소스 파일이 최소 한 개의 테스트에서 import 된다
[위반] export 된 모든 심볼이 어딘가에서 참조된다
```

둘 다 **검사기에 맹점이 있다.** 그리고 둘 다 자기 출력에 그 사실을 적고 있었다 —
*"(재export·동적 import 는 이 검사가 보지 못합니다)"*. 맹점을 아는 판정을 `violated`
로 올렸고, 그래서 차단할 수 없었고, 차단할 수 없으니 종료 코드를 버렸다.

**대가**: 같은 명령 안의 **맹점 없는 판정**까지 차단력을 잃었다.

| 판정 | 맹점 | 차단했어야 하나 |
|---|---|---|
| 죽은 npm 스크립트 (TS-012 의 결함) | 없음 | **그렇다** |
| 선언된 라우트가 등록되지 않음 (TS-013 의 결함) | 없음 (TS-017 에서 오탐 3건 수정) | **그렇다** |
| 미테스트 소스 | 동적·전이 import | 아니다 |
| 미참조 export | 재export·동적 import | 아니다 |

이 프로젝트가 가장 자랑하는 두 수정(TS-012·TS-013)의 재발 방지 검사가 **꺼져 있었다.**

## Root cause

**판정 어휘에 "사실이지만 차단 근거가 서지 않는다"는 칸이 없었다.**

`verdict` 는 `ok` / `violated` / `needs-intent` 셋뿐이었다. 맹점 있는 검사 결과를
넣을 자리가 `violated` 밖에 없었고, 그러면 CI 가 빨간불이 되므로 `|| true` 가 붙었다.

이것은 이 프로젝트가 **다른 세 곳에서는 이미 해결한 문제**다. 돌연변이에는
`out-of-spec`(명세가 요구하지 않음)이 있고, 독립성에는 `hard-coded`(등급을 내리지
않음)가 있고, 노출 진단에는 `unknown`(묻지 못했다)이 있다. 검수에만 없었다.

## Fix

### 1. `advisory` 를 추가한다

```
ok         맹점 없음, 일치한다
violated   맹점 없음, 어긋난다        → 종료 코드 1 (차단)
advisory   **맹점 있음**, 어긋나 보인다 → 보고만
needs-intent  의도가 필요하다          → 보고만
```

기준을 **출력에 적는다.** 적지 않으면 다음 사람이 "권고도 위반인데 왜 안 막나"로
읽고 다시 합친다.

```
위반 = 차단 근거가 서는 판정 (검사기에 맹점이 없다) → 종료 코드 1
권고 = 사실이지만 검사기에 **알려진 맹점**이 있다 → 차단하지 않는다
```

### 2. 맹점 자체를 줄인다 — 전이 import 를 따라간다

`advisory` 로 내리는 것만으로는 오탐이 남는다. 맹점 중 **고칠 수 있는 것**을 고쳤다.

이전 구현은 테스트가 **직접** import 하는 파일만 셌다. 테스트가 `App.tsx` 를
import 하고 `App.tsx` 가 `Layout.tsx` 를 import 하면 `Layout.tsx` 는 실행되는데도
'미테스트'로 보고됐다. 전이 폐쇄를 따라가도록 바꿨다. 그리고 `.d.ts` 는 실행될
코드가 없으므로 세지 않는다.

실측:

```
직접 import 기준   14건 보고
전이 import 기준   12건 실제
                   ─────
오탐               2건 (14%)  LoadingSpinner.tsx, WeeklyCompletionChart.tsx
.d.ts 제외 후      11건
```

### 3. `|| true` 를 뗀다

```
전:  위반 2 · 통과 8        → 종료 코드 1 → `|| true` → 아무것도 막지 않음
후:  위반 0 · 권고 2 · 통과 8 → 종료 코드 0 → **차단력 복구**
```

이제 죽은 npm 스크립트가 생기거나 선언된 라우트가 등록되지 않으면 **CI 가 막는다.**


마지막 검사가 핵심이다 — `|| true` 가 다시 붙으면 실패한다. 이 결함은 **코드가 아니라
CI 설정에** 있었으므로 CI 설정을 검사한다.

## Lesson

**차단하지 못하는 판정을 차단 자리에 놓으면 그 자리 전체가 꺼진다.**

`|| true` 는 게으름이 아니라 **합리적 대응**이었다. 오탐 섞인 판정으로 빨간불을 내면
사람이 CI 를 무시하기 시작하고, 그게 더 나쁘다. 문제는 그 대응이 **같은 명령 안의
정확한 판정까지 끌어내렸다**는 것이다.

그래서 규칙은: **판정의 확신 수준을 판정 자체에 담아라.** 한 명령이 확신도가 다른
여러 사실을 내놓을 때, 종료 코드는 **가장 확실한 것들만** 반영해야 한다. 확신 없는
사실은 지우지 말고 — 지우면 정보가 사라진다 — 다른 칸에 담는다.

이 프로젝트는 그 칸을 세 번 만들었다(`out-of-spec`·`hard-coded`·`unknown`). 네 번째를
만들지 않은 곳이 하필 **차단 자리**였다.
