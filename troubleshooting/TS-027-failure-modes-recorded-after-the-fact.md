## Symptoms

증상이 아니라 **구조적 공백**이다. 그래서 severity 가 medium 이다 — 아직 아무것도
터지지 않았지만, 터질 때 알 방법이 없었다.

`troubleshooting/` 의 26건은 전부 **터진 뒤에** 쓰였다. 기록은 재발을 막는다.
그런데 하네스를 새 프로젝트에 붙이는 사람에게는 그 기록이 **26개의 산문**이고,
"내 프로젝트에 해당되는 것이 무엇인가"는 손으로 판단해야 했다.

[TS-025](TS-025-single-subject-verification.md) 가 그 판단이 틀린다는 증거다.
하네스는 "모든 프로젝트에 붙는다"고 선언했고 회귀 검증도 녹색이었는데, 두 번째
프로젝트에서 결함 5개가 나왔다. 넷은 `web_target` 의 모양에서 **증상이 없는**
것이었다 — 읽는 사람이 그걸 알 방법이 없었다.

구체적으로 이런 질문에 답할 장치가 없었다.

```
내 프로젝트에 .harness.json 이 없으면 어떤 게이트가 틀린 판정을 내는가?
typecheck 커맨드가 없는 프로젝트의 돌연변이 점수는 믿을 수 있는가?
내가 쓰는 런너는 실제로 검증된 적이 있는가?
```

## Root cause

**기록의 형식이 산문이었다.** 산문은 사람이 읽어야 하고, 읽는 사람은 26건 전부를
자기 프로젝트에 대입해보지 않는다. 기록을 **질의 가능한 형태**로 만들지 않은 것이
원인이다.

이것은 이 프로젝트가 반복해 온 패턴의 거울상이다 — TS-006 은 "절차를 문서에, 판정을
코드에" 두어 해결했다. 그런데 **실패 모드 자체**는 여전히 문서에만 있었다.

## Fix — `cli exposure`

### 문서가 선언하고 코드가 검사한다

노출 조건을 파이썬 딕셔너리에 적으면 문서와 코드가 **두 개의 진실**이 된다.
그것이 [TS-007](TS-007-dead-checkpointer-config.md)·[TS-019](TS-019-dead-config-and-orphan-code.md)
가 두 번 반복한 '죽은 설정'이다. 그래서 선언은 **TS 문서의 frontmatter 에만** 둔다.

```yaml
guard: `cli deadcode` 가 참조 0건 설정을 CI 에서 차단한다
exposure: dead-config
```

`cli exposure` 가 문서를 읽어 키를 해소하고, **양방향으로 강제**한다.

| 어긋남 | 처리 |
|---|---|
| 선언된 키에 검사기가 없다 | 보고 + 종료 코드 1 |
| 검사기가 있는데 아무 문서도 선언하지 않았다 | 보고 + 종료 코드 1 (고아 검사기) |

락파일 검사와 같은 모양이므로 오탐이 구조적으로 불가능하다 (TS-024 의 방식).
실제로 이 강제가 작동했다 — 처음 구현에서 `runner-executable` 검사기를 만들고
아무 문서도 선언하지 않았고, 첫 실행이 고아로 보고했다. TS-006 은 결함이 둘
(게이트가 권고였다 + `run_tests` 가 Windows 에서 한 번도 동작하지 않았다)이므로
한 검사기가 두 조건을 함께 묻도록 합쳤다.

### 판정은 네 가지, 점수는 없다

```
protected   노출 조건이 있고 가드가 작동한다
exposed     노출 조건이 있고 가드가 없거나 꺼져 있다
n/a         그 실패가 가능한 모양이 아니다
unknown     기계로 물을 수 없다 — 사람이 봐야 한다
```

점수를 쓰지 않는 이유는 `EVAL_WEIGHTS` 다 — 근거 없는 상수로 판정하면 그 수치를
방어할 방법이 없다. 각 항목은 **기계로 확인한 사실 하나**다.

`unknown` 을 `n/a` 로 합치지 않는다. "묻지 못했다"를 "해당 없다"로 적으면 측정
실패가 안전으로 위장된다 ([TS-016](TS-016-vacuous-evidence-passes-the-gate.md) 의 규칙).

### 노출 건수로는 차단하지 않는다

노출은 결함이 아니라 **조건**이다. `.harness.json` 이 없는 프로젝트는 노출이지만
그것이 잘못은 아니다 — 알고 쓰면 된다. 건수로 차단하면 "노출 0건을 만들기 위해
진단을 끄는" 압력이 생긴다. 차단하는 것은 **선언과 검사기의 어긋남**뿐이고,
그것은 조건이 아니라 사실 오류다.

### 실측 — 모양마다 다른 진단이 나온다

```
web_target                   노출 1 · 보호됨 19 · 해당없음 4 · 확인불가 2
fixtures/vanilla-js          노출 3 · 보호됨 17 · 해당없음 4 · 확인불가 2
fixtures/pytest-app          노출 2 · 보호됨 18 · 해당없음 5 · 확인불가 1
harness_project (자신)        노출 3 · 보호됨 14 · 해당없음 8 · 확인불가 1
```

같은 결과만 낸다면 진단이 아니다. 실제로 갈리는 항목의 예:

```
TS-021  typecheck 커맨드가 없으면 노출 — 구문을 파괴한 변이가 '테스트가 잡았다'로
        계수되어 돌연변이 점수가 과대평가된다. 픽스처 둘 다 노출, web_target 은 tsc 로 보호
TS-025  런너 실행 계층을 CI 가 돌리는 것은 jest 뿐 — vitest·pytest 는 노출
TS-006  vanilla-js 는 vitest 가 설치되지 않아 **게이트가 모든 기능을 거부**한다
```

## 이 명령을 만들면서 나온 결함 3건

진단기를 만드는 것 자체가 검사였다.

### 1. `.env` 가 실제 환경 변수를 이겼다 — **죽은 가드**

```python
load_dotenv(override=True)      # 이전
load_dotenv(override=False)     # 수정
```

CI 와 README 는 `GOOGLE_API_KEY=""` 로 토큰 없는 경로를 **"강제한다"**고 선언한다.
`override=True` 는 `.env` 가 그 환경 변수를 이기게 했으므로, `.env` 가 있는 로컬에서
그 선언은 **아무 일도 하지 않았다.** CI 에서는 `.env` 가 gitignore 되어 없기 때문에
우연히 동작하고 있었다.

선언된 가드가 실제로는 꺼져 있는 것 — TS-007·TS-019 와 같은 모양이고, 이것이
**죽은 설정의 세 번째 사례**다.

어떻게 발견했는가: 노출 진단이 `GOOGLE_API_KEY=""` 로 돌렸는데도 "API 키가 설정되어
유료 경로를 쓸 수 있다"고 보고했다. 진단기가 자기를 실행한 환경에 대해 사실을
말했고, 그 사실이 문서와 모순됐다.

### 2. `status.check` 에 인자를 거꾸로 넘겼다

`check(project_root, harness_root)` 인데 `check(harness_root)` 로 불러
`FileNotFoundError` 가 났다. 진단이 그것을 **'확인불가 + 예외 내용'** 으로 보고해서
즉시 드러났다. 예외를 삼켜 `n/a` 로 적었다면 영원히 몰랐을 것이다 — 그래서
검사기의 예외는 `unknown` 으로 잡고 예외 문구를 사유에 담는다.

### 3. TS-024 검사기가 외부 프로젝트를 거짓 양성으로 보고했다

`docs/status.md` 는 하네스가 **자기 대상**에 대해 생성하는 파일이다. 픽스처를
진단하면서 그 파일과 비교하면 당연히 어긋나고, 그것을 '노출'로 적었다.

수정: 진단 대상이 하네스의 **선언된** 대상일 때만 드리프트를 묻고, 그 밖에는
`unknown` 이다. 여기서 또 하나가 걸렸다 — `config_for` 는 target 을 넘긴 경로로
**덮어쓰므로**(TS-025 의 격리 규칙) '하네스가 선언한 대상'을 물으려면 `load` 를
써야 한다. `config_for` 로 물으면 항상 자기 자신이 나와 비교가 무의미해진다.

## Verification

```
python verification/repro_ts027.py
```

음성 대조를 포함한다 (verification 설계 규약 1):

```
PASS  음성 대조: .env 값과 빈 값은 구별 가능한 입력이다
PASS  외부 프로젝트의 TS-024 는 확인불가다 (노출도 해당없음도 아니다)
PASS  예외를 던진 검사기는 확인불가로 보고된다

```

가장 중요한 검사는 **모든 문서가 `exposure:` 를 선언했는가**와 **고아 검사기가
없는가**다. 둘 중 하나라도 어긋나면 "노출 n건"이 믿을 수 없는 값이 되므로
종료 코드 1 로 차단한다.

## 한계 — 이 진단이 **하지 않는** 것

| 묻지 못하는 것 | 왜 |
|---|---|
| 광고된 명령이 실제로 도는가 (TS-012) | 돌려봐야 안다. `unknown` 으로 적고 "CI 에서 전부 실행하는지 확인할 것"을 함께 출력한다 |
| 외부 프로젝트가 수치를 산문에 박아 두었는가 (TS-024) | 그 프로젝트의 문서 관행을 알 수 없다 |
| 피험체 앱의 구현 결함 (TS-011) | 임의 프로젝트에 대해 기계로 물을 조건이 없다. `n/a` 로 적고 그 이유를 쓴다 |
| 런너가 실제로 커버리지 줄 지도를 만드는가 (TS-026) | 리포터 **플래그 선언**까지만 본다. 실제 출력은 돌려봐야 안다 |

`unknown` 4건이 남아 있는 것이 이 명령의 정직한 상태다. 그 수를 줄이는 방법은
검사기를 더 똑똑하게 만드는 것이 아니라 **실제로 돌려보는 계층을 늘리는 것**이고,
그것은 TS-025 가 기록한 같은 공백이다.

## Lesson

**기록을 질의 가능한 형태로 만들지 않으면 읽는 사람이 대입해야 한다.**

이 프로젝트는 "절차는 문서에, 판정은 코드에" 를 TS-006 에서 배웠다. 그 원칙을
**실패 모드 자체**에는 적용하지 않고 있었다 — 26건이 산문으로만 존재했다.

그리고 진단기를 만드는 것 자체가 검사였다. 세 결함 모두 **진단기가 자기를 실행한
환경에 대해 사실을 말했기 때문에** 드러났다. 노출 진단의 값은 "노출 n건"이라는
수치가 아니라 **선언과 실제를 한자리에 놓는 것**이다.
