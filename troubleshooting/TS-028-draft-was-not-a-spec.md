## Symptoms

`cli inspect --write-draft` 는 "명세 초안"을 만든다고 선언했다. 실측한 초안 4건 전부:

```
F-001  "모든 소스 파일이 최소 한 개의 테스트에서 import 된다"   ← 코드 위생 규칙
F-002  "export 된 모든 심볼이 어딘가에서 참조된다"               ← 코드 위생 규칙
F-003  "LoginForm 의 입력 검증 규칙"                            ← 주제, 내용 없음
F-004  "UserMenu 의 실패 시 동작"                               ← 주제, 내용 없음
```

**넷 다 명세가 아니다.**

앞의 둘은 **앱의 기능이 아니다.** 사용자가 관찰할 수 있는 행동이 없고 `steps` 를
채울 방법도 없다 — "모든 소스가 테스트에서 import 된다"에 태그 테스트를 붙일 수 없다.
`features.json` 에 넣으면 게이트가 기능 아닌 것을 기능으로 센다.

뒤의 둘은 **"명세가 필요한 자리"를 가리키지만 내용이 없다.** `steps: []` 이고
`description` 이 주제어다. 사람이 받아서 할 일은 빈 종이에 쓰는 것과 같다 — 사용자가
요청한 것은 *"내가 쓰기 전에 네가 판단해서 명세를 만들어 둔다"* 였고, 그것이 안 됐다.

덤으로 ID 가 `F-001` 부터 시작했다. `features.json` 에 이미 `F-001` 이 있다.
초안을 그대로 옮기면 **명세가 덮이거나 중복된다.**

## Root cause

**초안을 만드는 코드가 없었다.** `draft_spec()` 은 검수 결과(`checks`)를 순회하며
`claim` 을 `description` 에 넣고 `steps: []` 로 감쌌다. 즉 **포장만** 했다.

```python
for c in checks:
    out.append({"id": ..., "description": c.claim, "steps": [], ...})
```

`c.claim` 은 **검사 항목의 이름**이다 ("모든 소스 파일이 … import 된다"). 그것을
`description` 자리에 넣으면 모양은 명세가 되지만 내용은 검사 항목이다.

왜 이 상태로 남았나 — 진짜 어려운 질문을 피했기 때문이다.

> **코드를 읽어서 명세를 쓰면 순환이 아닌가?** ([TS-013](TS-013-unit-tests-cannot-verify-route-table.md))

그 질문에 답하지 않고 "초안이니까 사람이 검토하면 된다"로 넘겼다. 그래서 초안의
**내용**에 대한 판단이 아예 없었다.

## Fix — 순환과 불변식의 경계를 긋는다

### 무엇이 순환이고 무엇이 아닌가

```
순환:    구현의 **제어 흐름**을 읽어 명세로 올린다
         if (!email.includes('@')) setError(...)
           → "이메일에 @ 가 없으면 오류를 표시한다"
         그 구현으로 그 구현을 검사한다. 항상 통과한다.

불변식:  **선언**을 읽고 **런타임 행동**을 검사한다. 두 지점이 다르다
         disabled={loading}
           → "loading 일 때 이 컨트롤이 비활성화된다"
         테스트는 상태를 움직여 DOM 을 읽는다. 배선이 끊기면 잡힌다.
```

### 그래서 **상태 조건부 선언만** 쓴다 — 실측으로 그은 선

```
disabled={loading}      값이 식  → 상태를 움직여 DOM 을 읽어야 한다   (두 지점)
role="main"             값이 리터럴 → 속성이 있는지 읽는다             (한 지점)
```

`role`·`aria-live`·`type` 에서 명세를 만들면 **뽑아낸 그 속성을 그대로 다시 읽는**
것이 되어 아무것도 검증하지 않는다. 제외했다. `web_target` 에서 실측한 분포:

| 선언 | 매칭 | 쓰는가 |
|---|---|---|
| `disabled={…}` | 3 | O — 상태 조건부 |
| `aria-invalid={…}` | 2 | O |
| `aria-busy={…}` | 1 | O |
| `aria-describedby={…}` | 2 | O |
| `role="…"` | 13 | **X — 무조건** |
| `aria-live="…"` | 2 | **X — 무조건** |
| `type="…"` | 3 | **X — 무조건** |
| `required` / `minLength` / `maxLength` / `pattern` | **0** | O — 거부 행동을 약속한다 |

검증 제약(`required` 등)은 값이 리터럴이지만 **거부 행동**을 약속하므로 검증 지점이
다르다 — "이 속성이 있다"가 아니라 "빈 값이 거부된다"다. 그런데 이 피험체에는
**하나도 없다.** 규칙만 쓰고 한 번도 매칭되지 않으면 '발견 0건'과 '검사기 고장'을
구별할 수 없으므로([TS-016](TS-016-vacuous-evidence-passes-the-gate.md)),
`verification/fixtures/vanilla-js/src/signup.jsx` 에 심어 고정했다
([TS-025](TS-025-single-subject-verification.md) 의 규약: 두 번째 모양으로 검증한다).

### 결과 — 전후 비교

```
전:  F-001  모든 소스 파일이 최소 한 개의 테스트에서 import 된다     (기능 아님)
     F-003  LoginForm 의 입력 검증 규칙                            (내용 없음)

후:  F-076  emailError 일 때 이메일 입력란에 설명이 연결된다
            ← src/components/LoginForm.tsx:156
              aria-describedby={emailError ? `${emailId}-error` : undefined}
     F-078  loading 일 때 비밀번호 입력란과 이메일 입력란이 비활성화된다
            · loading 일 때 비밀번호 입력란이 비활성화된다
            · loading 일 때 이메일 입력란이 비활성화된다
     F-081  !isValid || loading 일 때 제출 버튼이 비활성화된다
```

세 가지가 달라졌다 — 행동 문장이고, `steps` 가 있고, **읽은 선언의 원문과 위치**가
붙어 있다.

### 셋으로 나눈다

| | 어디로 | 왜 |
|---|---|---|
| 상태 조건부 선언 | **초안** | 검증 지점이 다르다 |
| 내용이 구현에만 있는 자리 | **질문** | 읽어서 올리면 순환이다. 사람이 내릴 결정을 적어 넘긴다 |
| 코드 위생 규칙 | **제외** | 기능이 아니다. 검수 보고(`checks`)에만 남는다 |

## 만드는 과정에서 나온 결함 4건

### 1. 정규식이 조건식을 잘랐다

```
aria-describedby={emailError ? `${emailId}-error` : undefined}
                  ^^^^^^^^^^^^^^^^^^^^^  ← [^}] 가 여기서 멈춘다
```

초안이 *"emailError ? \`${emailId 일 때 …"* 라는 문장을 냈다. 템플릿 리터럴의 중첩
중괄호 때문이다. **정규식으로 괄호를 맞출 수 없다** —
[TS-021](TS-021-mutation-operators-tested-the-compiler.md) 에서 `if (X)` 변이가 같은
이유로 깨졌고, 같은 처방(중괄호를 세는 전용 함수)을 썼다.

### 2. 삼항 전체를 조건으로 썼다

`emailError ? X : undefined` 의 조건은 `emailError` 다. 최상위 `?` 앞까지만 남긴다.
`!!x` 는 `x` 로 줄인다(이중 부정은 참/거짓 변환이므로 의미가 같다). **번역은 하지
않는다** — `emailError` 가 무엇을 뜻하는지는 코드가 알고 나는 모른다. 추측해서
"이메일에 오류가 있을 때"로 쓰면 초안에 없는 의미가 섞인다.

### 3. 요소를 변수 이름으로 불렀다

*"emailId 가 비활성화된다"* — 읽는 사람에게 아무 의미가 없다. `<label htmlFor>` 의
글자를 읽어 *"이메일 입력란이 비활성화된다"* 로 바꿨다. 라벨은 **사용자가 실제로 보는
글자**다. 그리고 조사를 받침에 맞게 골랐다 — *"제출 버튼**가**"* 가 실제 출력이었고,
초안은 사람이 **읽고 판단할** 문장이므로 읽히지 않으면 목적을 잃는다.

### 4. ID 자릿수를 기존 ID 에서 추정해 형식을 위반했다

픽스처는 `APP-01`·`APP-02` 를 갖고 `id_pattern: "APP-\d{2}"` 를 선언한다. 기존 ID 의
폭에서 추정하는 구현이 **`APP-003`** 을 냈고 그것은 형식 위반이라 `cli tags` 가
거부한다. 자릿수는 **선언된 형식**에서 읽어야 한다. 자릿수를 넘는 번호
(`APP-\d{2}` 에서 100 번째)는 내지 않는다.

### 5. 회귀 검증이 **이 결함을 고정하고 있었다**

`repro_ts017.py` 의 블록 [10] 은 이렇게 단정했다.

```python
check("출처가 박힌다", draft[0]["origin"], "inspect:dead-script")
check("ID 접두사 반영", draft[0]["id"], "F-001")
```

**둘 다 결함을 고정한 단정이다.** 앞의 것은 코드 위생 규칙이 초안에 들어가는 것을
"출처가 박힌다"로 통과시켰고, 뒤의 것은 `F-001` 이라는 **충돌하는 ID** 를 정답으로
못박았다. 그래서 수정하자 회귀 검증이 깨졌고, 그 깨짐이 옳았다.

[TS-024](TS-024-published-numbers-go-stale.md) 가 적은 원인 1 —
*"도구와 그 도구의 테스트를 같은 사람이 같은 이해로 만든다"* — 가 또 나왔다.
`draft_spec` 을 쓴 사람과 그 테스트를 쓴 사람이 같았으므로, 테스트는
"초안이 명세인가"를 묻지 않고 "`draft_spec` 이 자기가 하는 일을 하는가"만 물었다.
단정 하나하나는 전부 통과했고 **질문 자체가 없었다.**

## 한계 — 정직하게 말해야 하는 것

**선언 기반 초안은 회귀 울타리이고 정확성 증명이 아니다.**

`disabled={loading}` 을 읽어 만든 명세는 *"저자가 로딩 중 비활성화를 의도했다"*를
전제한다. 저자가 **틀린 것을 선언했다면** 초안은 그 버그를 명세로 고정한다.
잡을 수 있는 것과 못 잡는 것:

| 잡는다 | 못 잡는다 |
|---|---|
| 선언과 런타임의 어긋남 (배선 끊김, 리팩터 사고) | 선언 자체가 틀렸다 |
| 회귀 — 되던 것이 안 되기 시작함 | 있어야 하는데 선언되지 않은 동작 |

그래서 모든 초안은 `source` 에 **원문과 위치**를, `review_question` 에 그 한계를
함께 담는다. 사람이 판단할 것은 빈 종이가 아니라 **구체적인 한 문장**이다.
그것이 이 수정이 주장하는 전부다.

## Lesson

**'초안'이라는 이름이 내용에 대한 판단을 면제해 주지 않는다.**

"사람이 검토할 것이니 대충 내도 된다"는 생각이 이 결함을 남겼다. 실제로는 반대다 —
사람이 검토해야 하기 때문에 **검토할 수 있는 형태**여야 한다. 기능 아닌 것과 내용
없는 주제를 섞어 내면 검토 비용이 빈 종이보다 커진다.

그리고 피했던 질문("코드를 읽어 명세를 쓰면 순환인가")에 답하자 **그 답이 곧 설계**가
됐다 — 상태 조건부 선언은 되고 무조건 속성은 안 된다는 선이 그것이다. 어려운 질문을
미루면 그 자리에 포장이 들어선다.
