# 하네스 — 토큰 없는 기능 구현 루프

이 세션이 **추론 엔진**이고, `python -m harness.cli` 가 **심판**이다.
유료 LLM API를 호출하지 않는다 (`main.py` / `night_shift.py` 는 쓰지 않는다).

## 철칙 — 네 가지 불신

1. **자기 보고를 믿지 않는다.** "구현했다"는 증거가 아니다. `mark` 가 통과시켜야 통과다.
2. **스위트 녹색을 믿지 않는다.** 전체 테스트가 통과해도 그 기능의 증거가 아니다.
   해당 기능 ID 를 인용하는 테스트가 있어야 한다.
3. **거부를 설득하려 하지 않는다.** `mark` 가 거부하면 사유를 읽고 **코드나 테스트를 고친다.**
   플래그를 직접 편집하거나 `HARNESS_REQUIRE_TEST_EVIDENCE=false` 를 쓰지 않는다.
4. **비가역적 작업은 사람에게 묻는다.** 배포·삭제·force push 는 승인 없이 실행하지 않는다.

## 절차

### 1. 작업 받기
```bash
python -m harness.cli next
```
다음 미구현 기능의 명세(`steps`)와 태그 규약을 출력한다.
특정 기능을 지정받았으면 `python -m harness.cli show F-005`.

### 2. 구현
명세의 `steps` 가 합격 조건이다. 한 세션에 **기능 하나만** 끝낸다.
기존 파일을 고치는 것을 우선하고, 같은 기능을 두 곳에 구현하지 않는다
(과거에 `UserMenu` 가 두 벌 생겨 앱은 미검증본을 렌더링하고 테스트는 고아를 검증했다 — TS-006).

### 3. 테스트 작성 — 태그가 없으면 증거가 아니다
```ts
describe('F-005: 인증되지 않은 사용자가 보호된 페이지에 접근 시 리다이렉트', () => {
  test('F-005.1: 비로그인 상태로 /dashboard 접속 시 /login 으로 이동한다', ...)
  test('F-005.3: 원래 URL 이 ?redirect= 로 보존된다', ...)
})
```
- 기능 태그 `F-005` 는 **필수**. 없으면 `mark` 가 거부한다.
- 단계 태그 `F-005.1` 은 선택이지만, 붙이면 단계 커버리지가 기록된다.
- **통과만 확인하는 테스트를 쓰지 않는다.** 구현이 없어도 통과하는 단정은 증거가 아니다.
  (`expect(true).toBe(true)` 류 금지)

### 4. 판정 확인 — 플래그를 바꾸지 않는 예비 검사
```bash
python -m harness.cli verify F-005
```
`[거부]` 면 사유를 읽고 3단계로 돌아간다. 사유는 네 종류다:
- `실패 테스트 N건` → 회귀. 다른 기능을 깨뜨렸다. 먼저 고친다.
- `F-005 를 검증하는 테스트가 없습니다` → 태그 누락.
- `태그 테스트 N건 실패` → 그 기능 테스트 자체가 실패 중.
- `명세 단계 [...] 가 검증되지 않았습니다` → `step` 수준에서만 발생.

### 5. 기록 — 유일하게 플래그를 쓰는 명령
```bash
python -m harness.cli mark F-005
```
전체 스위트를 실행하고 통과하면 `features.json` 에 근거 테스트 이름과
단계 커버리지를 함께 기록한다. 종료 코드 0 = 반영, 1 = 거부.

### 6. 커밋
```bash
git add -A && git commit -m "feat(F-005): 보호된 페이지 리다이렉트"
```
기능 코드와 테스트만 포함한다. `.env` 는 절대 커밋하지 않는다.

### 7. 새 실패 모드를 만났으면 기록
증상 → 근본 원인 → 수정 → 검증 → 예방 순서로 `troubleshooting/TS-0NN-*.md` 를 쓴다.
형식은 `troubleshooting/_template.md`, 기존 사례는 `troubleshooting/INDEX.md` 참조.
**같은 함정을 두 번 밟지 않기 위한 장치다.** 추측이 아니라 재현한 사실만 적는다.

## 점검 명령

```bash
python -m harness.cli audit      # 통과로 기록된 기능 전수 재검증
python -m harness.cli report     # 게이트 판별력 + 실행 로그 측정
cd web_target && npx jest . --no-coverage   # 테스트만 (npm test 는 커버리지 임계로 exit 1)
```

`audit` 이 거부를 내놓으면 과거 통과가 지금 기준을 못 넘는다는 뜻이다 —
테스트를 보강하거나 `unmark` 로 정직하게 되돌린다.

## 독립 검증을 원하면 (선택)

구현한 세션이 자기 작업을 채점하면 편향된다. 서브에이전트에게
"이 기능의 테스트가 명세 `steps` 를 실제로 검증하는지 확인해달라"고 맡기면
구현자와 채점자가 분리된다. 게이트는 **테스트 이름과 통과 여부만** 보므로
"테스트가 제대로 검증하는가"는 여전히 사람이나 다른 에이전트의 판단이 필요하다.

## 하지 말 것

- `features.json` 을 직접 편집 (게이트를 우회하는 것이다)
- `HARNESS_REQUIRE_TEST_EVIDENCE=false` 사용 (운영자 전용 디버깅 수단)
- `python main.py` / `python night_shift.py` 실행 (유료 Gemini API를 호출한다)
- 테스트를 구현에 맞춰 느슨하게 고치기 (단정을 약화시키면 증거가 사라진다)
- 한 세션에 여러 기능 동시 구현
