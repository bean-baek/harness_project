# 반드시 레포 루트에서 실행한다 (아래 '실행 위치' 참조)

**건수를 적지 않는다 (TS-024).** 스크립트가 바뀌면 이 표의 숫자가 조용히 거짓이 된다 —
같은 종류의 드리프트로 README 가 같은 측정값을 네 번 다르게 발표한 적이 있다.
각 스크립트는 실행하면 `PASS n / FAIL 0` 을 직접 출력하고, 실패 시 종료 코드 1 을 돌린다.
CI 가 그 종료 코드를 확인하므로 '총 n건'이라는 수치는 검증 없이 떠다니는 값이었다.

`repro_bug.py` 는 회귀 검증이 아니다 — Gemini API 키가 유효한지 단독으로 확인하는
도구이며 **실제로 API 를 호출한다**(유료). `llm_errors.py` 의 인증 실패 안내가
이것을 가리킨다.

## 실행 위치 — 루트에서 실행할 것

각 스크립트는 `PROJECT = Path(__file__).resolve().parent.parent` 로 레포 루트를
`sys.path` 에 넣지만, **일부 검증은 `"web_target"` 을 상대 경로로 쓴다**
(`repro_ts016.py` 의 태그 파일 탐색 등). 따라서 작업 디렉터리가 레포 루트여야 한다.

```bash
cd /path/to/harness_project
python verification/repro_ts016.py     # OK
cd verification && python repro_ts016.py   # 실패 — web_target 을 찾지 못한다
```

CI 도 루트에서 실행한다.

## 설계 규약

이 스크립트들이 공유하는 세 가지 원칙이다.

**1. 음성 대조를 반드시 포함한다.** "통과해야 하는 것이 통과한다"만 보면 기준을
보증하지 못한다 — 모든 입력을 통과시키는 기준도 그 테스트를 만족시킨다.
그래서 각 스크립트는 **거부돼야 하는 입력이 실제로 거부되는지**를 함께 단정한다.

**2. 측정기 자신이 작동하는지 먼저 묻는다.** "발견 0건"은 검사기가 고장 난 상태와
구별되지 않는다(TS-016). `repro_ts019.py` 가 가장 분명한 예다 — 일부러 결함을 심은
임시 프로젝트를 검사기에 먼저 주고, 잡는 것을 확인한 뒤에 실제 레포가 깨끗함을 단정한다.

**3. 외부 의존을 스텁한다.** jest·tsc·LLM 호출은 전부 스텁이다. 그래야 API 쿼터와
무관하게 재현되고 CI 에서 키 없이 돈다. 예외는 `repro_bug.py` 뿐이다.

**4. 일반화를 주장하는 코드는 두 번째 모양으로 검증한다 (TS-025).** 설정으로 뺀 것과
**다른 값이 실제로 동작하는 것**은 다른 명제다. 전자는 코드를 읽으면 확인되고 후자는
다른 값을 넣어 돌려봐야 확인된다. 1~3 을 전부 지킨 회귀 검증이 결함 5개를 놓쳤는데,
이유는 촘촘하지 않아서가 아니라 **전부 같은 피험체(`web_target`)를 봤기** 때문이다.
그래서 `fixtures/` 에는 런너·규약·ID 형식·언어·설정 위치가 전부 다른 프로젝트를 둔다 —
`web_target` 에서는 다섯 결함 모두 **증상이 없다.**

## 새 스크립트를 추가할 때

트러블슈팅 문서(`troubleshooting/TS-0XX-*.md`)와 **쌍으로** 만든다.
문서는 무엇이 왜 깨졌는지, 스크립트는 그것이 다시 깨지지 않는지를 담는다.
추가 후 세 곳을 갱신한다.

1. `.github/workflows/ci.yml` — 실행 단계
2. `README.md` / `README_EN.md` — §10 회귀 검증 목록과 검증 건수
3. 이 파일의 표
